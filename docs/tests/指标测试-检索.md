## 一、前置条件

### 1.1 基础设施

通过 `docker compose up -d` 启动以下服务（docker-compose.yml 已在 M1 配置）：

| 服务 | 端口 | 用途 | 验证命令 |
|---|---|---|---|
| PostgreSQL | 5432 | 文档/分块/索引元数据 | `docker compose ps postgres` |
| Milvus | 19530 | 向量存储与召回 | `docker compose ps milvus` |
| Redis | 6379 | 检索结果缓存 | `docker compose ps redis` |
| MinIO | 9000 | 文档原始文件存储 | `docker compose ps minio` |

### 1.2 环境变量

在 `.env` 文件或 PowerShell 环境中配置：

```powershell
$env:KNOWFLOW_EMBEDDING_MODEL = "BAAI/bge-m3"
$env:KNOWFLOW_POSTGRES_PASSWORD = "nexus"
$env:KNOWFLOW_REDIS_URL = "redis://localhost:6379/0"
$env:KNOWFLOW_MILVUS_URI = "http://localhost:19530"
```

### 1.3 模型缓存

首次运行会自动下载 embedding 模型（约 2GB），需确保网络畅通：

- `BAAI/bge-m3`（embedding，dim=1024）

模型缓存目录默认为 `~/.cache/huggingface/`，可通过 `HF_HOME` 环境变量调整。

### 1.4 数据库初始化

```powershell
# 建表（PG）
uv run python scripts/init_db.py

# 建 Milvus collection（HNSW + IP 度量）
uv run python scripts/init_milvus.py
```

### 测试 3：缓存命中验证

**目的**：验证 Redis 缓存对重复查询的加速效果，以及文档变更后缓存失效。

**说明**：缓存键由 query + 检索参数（top_k / with_rerank）共同决定，只有 query 与参数完全一致才会命中；文档索引/删除成功后全部检索缓存自动失效。

**步骤**：

```powershell
# 首次查询（cache miss）
# 记录 latency_ms

# 同一 query 且同一检索参数再次查询（cache hit）
# 记录 latency_ms，应显著下降

# 同一 query 但不同 top_k（cache miss，参数不同不命中）
# 上传/删除一份文档后，同一 query 同一参数再次查询（cache miss，文档变更已失效）
```

**预期结果**：

- 首次查询 `cache_hit=False`
- 二次查询（同 query 同参数）`cache_hit=True`，latency 下降 50%+
- 换 top_k 或 with_rerank 后查询 `cache_hit=False`
- 索引/删除文档后再次查询 `cache_hit=False`（旧缓存已清空）
- Redis 中可查到 key（md5(query+参数) 前缀）

**结果记录**：

## 五、备注

- **静态模式局限性**：`run_eval.py --mode static` 使用 fake 组件（hashing embedding / 词项重叠精排），仅用于验证 pipeline 链路打通与报告格式，**不作为真实指标的验收依据**。
- **真实模式预期提升来源**：
  1. bge-m3 embedding 捕获语义相似性（vs hashing trick）
  2. 向量 + BM25 双路互补（语义 + 关键词）
  3. 精排将相关结果前置（MRR 提升）
- **指标不达标时**：如实记录实测值与差距，分析原因（语料规模 / 模型选择 / 评测集质量），不伪造数据。
