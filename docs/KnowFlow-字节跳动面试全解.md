## 0. 使用说明与诚实边界（必读）

### 0.1 项目一句话定位（自我介绍第一句）

> **标准回答**："KnowFlow 是一个企业知识库 Agent 平台，面向企业内部异构文档的知识问答与研究报告场景。它不是简单的 RAG 问答，而是解决了四个工程问题的完整 Agent 平台：**检索的召回**（混合检索）、**工具调用的治理**（执行域隔离）、**复杂任务的编排**（Multi-Agent + Deep Research 报告链路）、**上下文的治理**（卸载 + 摘要）。四个问题都有脚本实测的量化指标支撑。"

### 0.2 诚实边界（红线，被追问时必须主动说明）

字节面试官对个人项目最敏感的几件事：**伪造数据、虚报规模、功能与简历不符**。以下边界必须如实陈述，背答案前先背这一段：

1. **无线上流量**：项目是独立开发 + 本地评测，没有真实用户/线上 QPS。被问到时："目前是个人项目，没有大规模线上数据，但我搭建了完整的本地评测体系（50 条标注查询、33 个工具场景、60 条 QA、4 组并发任务集），所有指标都是脚本实测、可复现，报告文件可查。"
2. **检索指标是"文档级展开判定"口径**：Recall@10 33.6% 是 2026-06-08 的 GraphRAG vs Hybrid 对比评测（合成语料 5 篇 43 块 + hashing embedding 静态模式）。最新的 `run_eval.py` 静态报告用 chunk 级判定口径，Recall@10 为 23%。**两套数字都是真的，区别只在"相关 chunk 怎么判定"**——详见第 3 章 Q16。
3. **FC 准确率 100% 是"静态代理指标"**：含义是"预期工具在隔离后的可见工具集中"的覆盖比例，不是真实 LLM 调用准确率。真实模式需 LLM Key 跑完整工具循环。
4. **并发下降 65.6% 是静态模式**：真实并发执行器 + 模拟子任务延迟（1.2-2.2s），不是线上真实请求。
5. **GraphRAG 对比 +8% 目标未达成**（实测 -1.0%），如实承认并说明原因（静态 embedding + 判定口径），同时给出跨文档场景的正向证据（MRR +0.0213）。
6. **一跳扩展已随"移除 PG 图谱检索"被删除**（详见第 3 章 Q9）；**向量服务异常→BM25 完整降级只落地了一半**（详见第 3 章 Q11）。这两处必须主动说明，面试官若懂代码一眼看穿，主动坦白反而加分。

## 1. 简历第 1 条：复杂任务编排（LangGraph + Multi-Agent + 报告链路）

**简历原文**：复杂任务编排：基于 LangGraph + checkpoint 搭建问答与报告双编排链路：主 Agent LLM 规划拆解、子 Agent 并发执行与断点续跑，端到端耗时较串行降 65.6%（8 任务 84.1%）；报告链路对标 Deep Research，动态大纲、受限预算迭代调研、分章并行撰写、三级递进审查，单环节失败自动降级。

### 1.1 项目深挖 Q&A（先背这些）

**Q1-1：先介绍一下你这个项目的整体架构，从用户请求到返回讲一遍完整链路。**

> **标准回答**：用户请求进来，先过 FastAPI 网关层（路由、鉴权、限流、Trace 注入），进入 ChatService。ChatService 先做会话校验、消息入库，然后**混合检索**（向量 + BM25 双路召回，RRF 融合，reranker 精排），同时**召回用户长期记忆**。之后走三选一的生成链路：
> 第一，简单任务走**直连链路**——组装 prompt（系统提示 + 历史窗口 + 检索上下文 + 记忆），LLM 直接生成；
> 第二，需要工具的任务走**工具编排链路**——ToolOrchestrator 先做意图识别、激活 Skill、计算可见工具集、把 JSON Schema 注入 LLM，然后跑最多 5 轮的工具调用循环，最终答案和工具调用记录一起落库；
> 第三，复杂任务走**多 Agent 编排链路**——LangGraph 状态机：understand（意图分类）→ plan（LLM 规划拆解子任务）→ execute（创建子 Agent 并发执行，子 Agent 带独立上下文、可跑自己的工具循环）→ summarize（LLM 汇总子结果）。全链路经 SSE 流式回传：先 retrieval 事件，再 tool_start/tool_end 事件，再 token 流，最后 done。每个环节的耗时和错误都记录到 Trace，可观测可回放。

> **要点**：先讲"分层"（网关→服务→编排→存储），再讲"三选一"，最后讲"SSE 事件序列"。面试官听完就知道你有全局观。

**Q1-2：为什么用 LangGraph？自己写状态机不行吗？**

> **标准回答**：选 LangGraph 有三个理由。第一，**状态机模型天然适配多步推理**——节点（understand/plan/execute/summarize）+ 条件路由（plan 后按 needs_delegation 路由到 execute 或 summarize），LangGraph 的 StateGraph 就是干这个的，语义清晰；第二，**原生 checkpoint 支持断点续跑**——这是我最看重的点，复杂任务执行到一半进程挂了，能从 checkpoint 恢复 channel 状态继续跑，这个序列化协议（channel versions/writes、pending writes 的合并规则）是经过验证的成熟实现，自己写非常容易出错；第三，**它是行业标准**——大厂 JD 高频关键词，社区生态成熟。我自己写过状态机，知道边界情况（并发写入、条件路由、状态版本冲突）有多坑，所以站到 LangGraph 肩上，我只关心业务节点，不重复造轮子。这个决策我记录在 ADR 0004 里。

**Q1-3：LangGraph 的图结构具体是怎样的？每个节点做什么？**

> **标准回答**：图结构是 `START → understand → plan → (条件路由) → execute → summarize → END`。状态是一个 TypedDict（AgentState），包含 query、intent、needs_delegation、plan、subtask_results、active_skills、agent_role、retrieval_context 等字段。**understand 节点**用规则做意图分类（simple/query/tool/complex/uncertain）；**plan 节点**：intent 是 complex/uncertain 时调主 Agent 的 LLM 规划（`MainAgent.plan`），输出子任务列表，否则标记 needs_delegation=False 走 summarize；**execute 节点**：创建子 Agent run 和委派记录落库，用 `run_concurrent` 并发执行，完成后记录里程碑 checkpoint、更新委派终态；**summarize 节点**：委派过就调 `main_agent.summarize` 汇总子结果，没委派就 direct_answer 直答。路由逻辑就一行：`needs_delegation` 为真走 execute，否则直接 summarize。

**Q1-4：子 Agent 并发是怎么实现的？超时和失败怎么处理？**

> **标准回答**：并发执行在 `agents/concurrent.py` 的 `run_concurrent`：每个子任务是一个可等待协程，先用 `asyncio.wait_for(coro, timeout)` 包一层（默认超时 60 秒，防止单子任务挂死拖垮整体），再用 `asyncio.gather(*coros, return_exceptions=True)` 全部并发执行，单子任务超时或异常只返回 `SubtaskResult(success=False, error=...)`，**不阻塞其他子任务、不影响整个 run**。子 Agent 内部还有一层兜底：输出质量门禁（少于 20 个字符视为无效输出）+ 携带原因重试 1 次。所以整条链路是"主 run 有降级，子任务有重试，双保险"。

**Q1-5：checkpoint 是怎么做的？thread_id 是什么？断点续跑流程是什么？**

> **标准回答**：checkpoint 用 LangGraph 原生 `AsyncPostgresSaver`（存 PostgreSQL，连接池用 psycopg 的 AsyncConnectionPool），表结构是 LangGraph 自带的，我通过 `thread_id` 隔离每个 Agent run——**thread_id 就是 agent_runs 表的主键 run_id**。每次 `graph.ainvoke(state, config={"configurable": {"thread_id": run_id}})` 执行，LangGraph 自动把每一步的 channel 状态写进 checkpoint。**断点续跑**的流程是：进程被 kill 后，用同一个 thread_id（和可选 checkpoint_id）重新调 `graph.ainvoke`，LangGraph 从最近 checkpoint 恢复 channel 状态继续执行，不需要从头跑；委派里程碑也会记录 checkpoint_id 到 task_delegations 表，可以精确定位到"第几个子任务完成"这个粒度。另外我封装了 CheckpointManager，提供 restore（按 thread_id 恢复状态）、lineage（沿 parent_config 回溯父子 run 链）两个 API。这个决策的论证在 ADR 0003/0004：为什么存 PG 而不是 Redis——checkpoint 是**持久化状态**，要求不丢、可恢复、支持并发事务，PG 的可靠性更合适；Redis 更多用于热数据缓存，丢了就没了。

**Q1-6：为什么 checkpoint 存 PostgreSQL 不存 Redis？（追问）**

> **标准回答**：checkpoint 的本质是"任务执行状态的持久化快照"，要求是**不丢失、可恢复、并发安全**。Redis 是内存数据库，虽然快，但持久化依赖 RDB/AOF 配置，异常掉电可能丢数据；而且 LangGraph 的 checkpoint 要存 channel 版本号、pending writes 这些结构化的多版本数据，需要事务性写入，PG 的 ACID 事务天然合适。另外项目里 PG 已经是业务主库，复用同一套连接池和运维体系，少一个组件。Redis 在项目里承担的是短期记忆、检索缓存、任务队列这些"丢了可以重建"的热数据。这是我写在 ADR 0003 里的决策：**checkpoint 是冷数据，Redis 是热数据，按访问模式分存**。

**Q1-7：子 Agent 和主 Agent 有什么区别？子 Agent 只是换个 prompt 再调一次 LLM 吗？**

> **标准回答**：不是。这个我专门设计过——**子 Agent 是"工具化"的**：它复用 ToolOrchestrator，以 SUBAGENT 角色跑完整的工具调用循环。三个关键区别：第一，**可见工具集不同**——`subagent_only` 执行域的工具（比如 search_tool）只有子 Agent 可见，主 Agent 看不到也调不到，这是执行域隔离体系对"角色"维度的延伸；第二，**上下文隔离**——子 Agent 只看到自己的任务描述 + 按需检索的结果，不注入主 Agent 的完整历史，各子 Agent 挂独立的上下文管理器，互不串扰；第三，**独立系统提示词**——子 Agent 用工具型 prompt（SUBAGENT_TOOL_PROMPT_TEMPLATE），模板里注入它可见的工具清单。所以子 Agent 是"一个有独立工具权限、独立上下文、能自己检索自己调用工具的执行单元"，不是一次简单的二次 LLM 调用。主 Agent 的规划 prompt 也会注入子 Agent 的可见工具清单，保证拆出来的子任务都是"工具可达"的，不会拆一个干不了的活。

**Q1-8：主 Agent 怎么知道子 Agent 能干什么？**

> **标准回答**：plan 节点的 prompt 里有一个 `{available_tools}` 占位符，值是 `tool_orchestrator.visible_tools_text(AgentRole.SUBAGENT)`——即按 SUBAGENT 角色计算出的可见工具文本清单。主 Agent 在规划时就能看到"子 Agent 手里有哪些工具"，因此它只会拆解工具可达的任务，比如"子 Agent 可以检索知识库、可以联网搜索"，那"调研 A 产品"就能拆，而"直接登录 ERP 改数据"这种工具不可达的需求就不会被拆成子任务。这是我在设计上刻意做的闭环：**规划的可执行性由工具可见性保证**。

**Q1-9：子任务之间上下文怎么隔离？会不会互相污染？**

> **标准回答**：三个隔离层：第一，每个子 Agent 的输入只有自己的任务描述 + 共享的预检索上下文（主 Agent 在编排前做的检索结果）；第二，子任务还会**按需再检索**——每个子任务用自己的任务文本单独检索知识库，检索失败或无结果才回退共享的预检索上下文，这样跨主题的任务（比如同时调研"销售数据"和"考勤制度"）不会串扰；第三，每个子 Agent 挂独立的 ContextManager 实例，窗口、预算策略互不影响。子 Agent 的工具调用记录会带 subtask_id 标注来源，SSE 事件里前端能看到"是哪个子 Agent 调了哪个工具"。

**Q1-10：子任务失败了怎么办？会影响整体吗？**

> **标准回答**：不影响。单子任务失败被标记为 failed，其他子任务照常并发执行；汇总阶段，主 Agent 汇总时会把失败子任务对应的章节如实标注为"该部分未能获取"，主 run 状态仍然是 completed。再加上前面说的质量门禁 + 1 次重试。所以整体设计原则是：**编排器对子任务失败是"优雅降级"，不是"整体失败"**，这对企业场景很重要——8 个子任务里挂 1 个，不能整个报告都废掉。

**Q1-11：端到端耗时降 65.6% 这个数据是怎么测的？基线是什么？**

> **标准回答**：这是 `scripts/benchmark_multiagent.py` 的静态模式评测：构造 4 组任务集（2/3/5/8 个子任务），每个子任务用模拟延迟覆盖真实检索/工具调用量级（1.2-2.2s）。**串行基线**：子任务逐个执行，总耗时 = 各子任务耗时之和；**并发执行**：走真实的 `run_concurrent`（asyncio.gather + 超时 + 降级）同时跑，总耗时 = 最慢子任务耗时。下降率 = (串行 - 并发) / 串行。实测：2 子任务 42.5%、3 个 62.2%、5 个 73.5%、8 个 84.1%，均值 65.6%。而且我把"实测下降率"和"理论下降率"（纯数学计算）做了对照——每组场景两者几乎一致（比如 8 子任务实测 84.1% vs 理论 84.0%），说明**执行器本身的调度开销可忽略**，下降主要来自并发本身。这个设计目标是最低 60%，均值 65.6% 是达标的。

**Q1-12：为什么 2 个子任务只降 42.5%？跟 8 个子任务的 84.1% 差这么多？**

> **标准回答**：这是并发的数学特性：并发收益 = 1 - 最慢子任务耗时 / 总耗时。2 个子任务时，最慢的那个占了总耗时的一半多，并行省下的只有"较快的那个任务的时间"，上限就是 50% 左右，实测 42.5% 已经接近这个理论值；子任务越多，分母（串行总耗时）越大，最慢者占比越小，收益越趋近 100%。8 个子任务实测 84.1% 与理论 84.0% 一致。所以这个指标的设计目标不是追求绝对数值，而是**验证"并发执行器正确实现了并发"**——实测与理论一致就是最好的证据。

**Q1-13：子任务之间有依赖怎么办？你们是不是只能并行独立任务？**

> **标准回答**：当前实现是"一轮委派、全并行"模型，面向的是**可并行拆解**的复杂任务（多主题调研、多产品对比、分章报告），这是最常见的企业场景。如果子任务之间有依赖（比如任务 B 依赖任务 A 的结果），LangGraph 本身支持多轮/多分支图结构，我目前的图是单轮并行，这是刻意收敛的简单性——先把 80% 的场景做好。这是已知的扩展点，我在设计文档里也标了：后续可以做"分阶段委派"，第一阶段结果作为第二阶段的输入。面试被问到就说清楚这是当前边界，并给出扩展方案。

**Q1-14：报告链路（Deep Research）是怎么设计的？**

> **标准回答**：报告链路是独立于问答编排器的六阶段流水线（`agents/report/`，ADR 0008 记录了为什么独立：问答链路产出单答案，报告链路产出结构化章节 + 引用溯源，两条链路的产出物和阶段完全不同，混在一起状态机就脏了）。六阶段是 **PLANNING → RESEARCH → SYNTHESIS → WRITING → REVIEW → DONE**，每一阶段通过 on_progress 回调上抛进度，任一阶段异常返回带 FAILED 状态的结果对象而不抛出。具体：
> - **动态大纲**：Planner 让 LLM 输出 JSON 大纲（标题 + 章节列表，每章带 2-4 个检索查询），解析失败回退单章节大纲；
> - **受限预算迭代调研**：Researcher 对每章做迭代式调研——初始查询 → 三源检索（知识库/长期记忆/联网）→ **LLM 缺口评估**（判断证据是否充分，输出 follow_up_queries）→ 追加查询再检索；最多迭代 2 轮、每轮最多 3 个追加查询，已执行过的查询不重复，这就是"受限预算"——防止调研无限膨胀；
> - **分章并行撰写**：复用 run_concurrent，各章节并行交给撰写器；
> - **三级递进审查**：Reviewer 先做**规则校验**（确定性：引用 `[n]` 是否越界、正文是否过短），再做 **LLM 支持度校验**（生成的结论是否被证据支持），最后**主动事实核查**（把章节里的陈述提取出来，用陈述本身当查询去交叉检索，判定 supported/contradicted/unverified，只有矛盾才打回）。不通过就携带问题清单重写问题章节一次，再复查一轮；
> - **落盘**：写进会话沙盒的 reports 目录（MinIO 后端）；**后台化**：ReportService 用 asyncio.create_task 后台生成，不阻塞用户。

**Q1-15：报告链路的"单环节失败自动降级"具体指什么？**

> **标准回答**：三个层面：第一，**阶段级**——六阶段任一阶段异常，ReportPipeline 返回带 stage=FAILED 和 error 的结果对象，不把异常抛给调用方，用户能明确看到"生成到第几步失败了、为什么"；第二，**调研级**——某一路检索源挂了（比如联网搜索不可用），Researcher 只降级该路，其余两路照常，证据不足时走缺口评估决定是否继续；第三，**撰写级**——某章撰写失败，只重写该章，不影响其他章节。整体原则和问答编排一致：**局部失败不扩散，能降级就降级，不能降级就明确报错**。

**Q1-16：为什么不用 AutoGen / CrewAI？跟 LangGraph 比差在哪？**

> **标准回答**：我调研过。AutoGen 和 CrewAI 更偏"多 Agent 对话协作"范式——Agent 之间通过消息互相对话、互相调用，适合开放式协作，但**执行流程不可控、状态不可见**，出了问题很难定位；而且它们的 Agent 抽象比较重，和我的"执行域隔离 + 工具治理"体系集成成本高。LangGraph 的优势是**显式的状态机 + 显式的数据流**：每个节点输入输出都是 state 的一部分，流程是确定性的（先规划、后执行、再汇总），配合原生 checkpoint 可以做断点续跑和可观测——这对企业级场景（要审计、要重放、要恢复）是刚需。我的核心诉求是"可编排、可控、可恢复"，LangGraph 最契合。

**Q1-17：这个项目最难的点是什么？（必问题）**

> **标准回答**：最难的是**子 Agent 工具化与执行域隔离的联动设计**。一开始子 Agent 只是"换个 prompt 再调一次 LLM"，我意识到这样多 Agent 没有存在价值。真正打通的关键是：子 Agent 以 SUBAGENT 角色复用 ToolOrchestrator 跑工具循环，`subagent_only` 域的工具只对子 Agent 可见，同时规划 prompt 注入子 Agent 的工具清单保证任务可执行。这三件事（角色 → 工具可见性 → 规划可执行性）是互相咬合的，任何一环断了，多 Agent 就退化成"贵一点的串行 LLM 调用"。第二个难点是 checkpoint 的正确接入——LangGraph 的 checkpoint 是"channel 级别的状态版本管理"，要理解它的恢复语义才能设计好 thread_id 和委派里程碑。

### 1.2 编排方向的技术八股（必背）

**Q1-B1：asyncio 是什么？协程和线程有什么区别？为什么 IO 密集用 asyncio？**

> **标准回答**：asyncio 是 Python 的异步 IO 框架，核心是**单线程事件循环**：一个线程跑一个事件循环，把所有 IO 操作注册成可等待对象，IO 就绪时才回调，线程不阻塞等待。协程是"可暂停可恢复的函数"，通过 await 让出控制权。区别：线程是操作系统调度的并发单位，协程是用户态调度；线程切换有内核开销、有 GIL 竞争，协程切换代价极小；**IO 密集场景**（网络请求、数据库查询）大部分时间在等 IO，asyncio 让线程在等待期间去干别的，吞吐远高于阻塞线程模型。**CPU 密集场景**协程没用，要用多进程或把计算丢给线程池。我项目里所有检索、LLM 调用、数据库操作都是 IO 密集，所以全链路 async。

**Q1-B2：asyncio.gather 和 asyncio.wait_for 分别解决什么问题？**

> **标准回答**：`gather` 是把多个协程并发调度，返回所有结果，可以配 `return_exceptions=True` 让单个失败不中断整体——我项目里子 Agent 并发就用它，一个子任务挂了其他照跑；`wait_for` 是给单个协程加**超时**，超时抛 TimeoutError 并取消协程——我用它给每个子任务包 60 秒上限，防止单子任务挂死拖垮整个 run。组合起来就是 `run_concurrent`：先 wait_for 限时，再 gather 兜底。

**Q1-B3：GIL 是什么？对 asyncio 有影响吗？**

> **标准回答**：GIL 是 CPython 的全局解释器锁，同一时刻只有一个线程能执行 Python 字节码。它对**多线程 CPU 密集**是瓶颈（多线程跑不满多核），但对 asyncio 影响很小——因为 asyncio 是单线程事件循环，本来就没有并行执行 Python 代码的需求，IO 等待期间锁是释放的。我项目里 CPU 密集的部分（embedding 计算如果走本地模型、分块处理）如果有，会考虑丢给进程池，目前 embedding/reranker 默认走 API，主要是 IO 等待。

**Q1-B4：状态机设计里"条件路由"和"并行分支"（LangGraph 的 conditional edges / parallel）了解吗？**

> **标准回答**：LangGraph 的 StateGraph 用 add_edge 定义确定边、add_conditional_edges 定义条件路由（我 plan 节点就用它：needs_delegation 为真走 execute，否则直接 summarize）；并行分支是 Fan-out/Fan-in——一个节点输出多路并行、汇总节点汇合，我的 execute 节点内部用 asyncio.gather 实现了等效的"扇出汇聚"。LangGraph 还有 Send API 做动态并行（每路不同参数），我当前一轮委派用 gather 就够了，Send 是后续扩展点。

**Q1-B5：什么是"断点续跑"？和"重试"的区别？**

> **标准回答**：重试是"从头再试一次"；断点续跑是"从中间状态接着跑"。断点续跑的前提是**状态可持久化、可恢复**：LangGraph 把每个 channel 的版本和写入记录下来，恢复时从最近 checkpoint 重建完整 state，然后从断点节点继续执行。我的场景里进程被 kill 后，用同一 thread_id 重新 ainvoke，就能接着跑而不是重头开始。这在长任务（报告生成几十秒到几分钟）里很关键——重头跑浪费已完成的检索和工具调用，而且外部副作用（比如已经写入的文件）可能重复执行。

**Q1-B6：LLM 规划（Plan-and-Execute）和 ReAct 的区别？你项目里分别用在哪？**

> **标准回答**：ReAct 是"边想边做"——思考、行动、观察循环，灵活但 token 消耗高、可能跑偏；Plan-and-Execute 是"先定计划再执行"——一次性规划好子任务，再逐项执行，可控、省 token。我项目里**主 Agent 的规划是 Plan-and-Execute**（understand → plan → execute → summarize），因为企业复杂任务的拆解依赖清晰；**工具调用循环内部是 ReAct 式**的——LLM 观察工具结果决定下一步，最多 5 轮。两者组合是工业界主流：大步骤用规划，小步骤用 ReAct。

**Q1-B7：LangGraph 和 LangChain 是什么关系？**

> **标准回答**：LangChain 提供 LLM 抽象层（ChatModel、PromptTemplate、工具的 bind_tools 等），LangGraph 是基于 LangChain 生态的**图状态机编排框架**——它复用 LangChain 的模型/工具/消息抽象，但专注"用图来描述 Agent 的控制流和状态"。我项目里 LangGraph 管编排，LangChain 的 ChatOpenAI 做模型接入、bind_tools 做工具绑定。LangGraph 比 LangChain 的旧 AgentExecutor 更可控（显式图结构），这也是我选它的原因之一。

## 2. 简历第 2 条：工具治理（执行域隔离 + Skill 体系）

**简历原文**：工具治理：基于 LangChain 工具注册表设计四类执行域隔离体系，按 Skill 激活状态动态裁剪模型可见工具集，声明式注册零侵入、依赖拓扑自动解析并拒绝循环。实测可见工具数降 43.4%、Schema Token 降 45.2%，FC 准确率 100%（33 场景，含工具混淆对抗用例）。

### 2.1 项目深挖 Q&A

**Q2-1：为什么要做工具治理？痛点是什么？**

> **标准回答**：核心痛点是**工具 Schema 全量注入的成本与准确率问题**。模型调用工具的前提是拿到工具的 JSON Schema（名称、描述、参数），工具越多，注入的 Schema 越大：token 成本线性上升，而且工具多了模型容易选错工具（FC 准确率下降）。我项目里内置 7 个工具，全量注入时平均要注入 504 个 token 的 Schema；实测执行域隔离后降到 276 个 token（-45.2%），可见工具数从平均 6 个降到 3.39 个（-43.4%）。企业场景工具会涨到几十上百个，这个治理机制是必须的——**不是优化，是规模化前置条件**。

**Q2-2：四类执行域是什么？为什么是"四类"？**

> **标准回答**：四类执行域定义在 constants.py 的 ExecutionDomain：**direct**（主 Agent 恒可见，如 calculator、retrieval_tool、memory_tool）、**skill_only**（Skill 激活后才注入，如 file_read/file_write/file_list 工具，随 data_analysis、document_summary 等 Skill 激活）、**subagent_only**（只有子 Agent 可见，如 search_tool）、**internal**（系统内部使用，永不对模型暴露，如记忆管理工具）。为什么是四类：它对应了**四个正交的可见性维度**——"是否随 Skill 激活"（skill_only vs direct）和"是否随角色变化"（subagent_only vs 主 Agent 可见）。direct 管基础能力、skill_only 管场景化能力、subagent_only 管角色权限、internal 管安全边界，四类就能覆盖企业场景的权限模型，再多就是过度设计了。

**Q2-3：VisibilityCalculator 是怎么计算可见工具集的？**

> **标准回答**：输入是（激活的 Skill 集合、Agent 角色、工具注册表），输出是可见 ToolDef 列表。逻辑分三步：第一步，收集所有激活 Skill 声明的工具名 + 依赖（Skill 的 tools 字段 + dependencies 字段）；第二步，遍历注册表中所有工具，跳过 internal 域；第三步，按规则过滤——direct 域恒可见；skill_only 域要求工具名出现在"激活 Skill 引用集合"里；subagent_only 域只对 SUBAGENT 角色可见。最后按注册顺序去重返回。**一个工具，同一时刻只被一个角色、一组激活 Skill 决定可见性**，这是整个治理体系的单点决策逻辑。

**Q2-4：Skill 体系是怎么设计的？SKILL.md 长什么样？**

> **标准回答**：Skill 是"声明式扩展点"——**零侵入**：新建一个 `skills/<name>/SKILL.md` 目录文件，启动时 skill_loader 解析文件首部的 YAML frontmatter 就完成注册，不需要改任何代码。字段有：name（必填）、description、tools（本 Skill 激活时可见的工具）、dependencies（依赖的其他 Skill）、domain（默认 skill_only）、enabled（默认 true）。比如 `skills/knowledge_qa/SKILL.md`：`tools: [retrieval_tool]`、`dependencies: [retrieval_tool]`、`domain: skill_only`。运行时 SkillManager 加载 skills 目录下所有 SKILL.md，支持 toggle 启停，active_skills() 返回当前激活集。新工具接入 = 注册到 ToolRegistry + 在某个 SKILL.md 里声明，两步完成。

**Q2-5：依赖拓扑解析和循环检测怎么做？**

> **标准回答**：`tools/dependency_resolver.py` 的 DependencyResolver：先收集 Skill 的 tools + dependencies，再把每个工具的 requires 传递依赖展开，最后做**DFS 拓扑排序**。循环检测用经典三色标记法（白/灰/黑）：DFS 过程中节点状态为"灰"（在递归栈中）时再次访问到，说明有环，直接抛 ValidationError 拒绝加载，比如"检测到循环依赖: A → B → A"。这样保证工具/Skill 的启用顺序可计算、无死锁。

**Q2-6：工具调用循环（ToolOrchestrator）完整流程是什么？**

> **标准回答**：流程是：意图识别激活 Skill → VisibilityCalculator 计算可见工具集 → 注入器把 ToolDef 转成 OpenAI function-calling 格式，`llm.bind_tools(tool_defs)` 绑定 → 进入最多 5 轮的循环（`max_tool_rounds=5`）：每轮 LLM 输出，如果有 tool_calls 就逐个执行——先过 PermissionChecker 越权检查，再执行工具、记录 ToolMetrics 指标，把结果回填给 LLM 继续下一轮；LLM 不再输出 tool_calls 就返回最终答案；5 轮耗尽返回 truncated 标记的占位答案。每轮工具调用的 ToolCallRecord（名称、参数、成功与否、耗时、错误）经 on_tool 回调上抛，最后序列化进消息表的 citations JSON 字段持久化——所以**每次工具调用都可审计、可回放**。

**Q2-7：为什么工具调用最多 5 轮？**

> **标准回答**：5 轮是"覆盖绝大多数真实场景"和"防止失控"的平衡点：企业知识问答通常 1-2 轮工具调用就能完成（检索 → 计算 → 回答），5 轮足够覆盖"检索→分析→计算→写文件→再检索"这种复杂链；同时上限防止模型陷入无限循环（比如反复调用同一工具）烧 token。设置是配置项 `max_tool_rounds`，可以调。真实场景如果超过 5 轮，说明任务设计有问题，应该被规划拆解而不是靠工具循环硬跑。

**Q2-8：PermissionChecker 做什么？工具越权怎么拦截？**

> **标准回答**：PermissionChecker 在工具执行前做**运行时越权拦截**：检查当前 Agent 角色是否有权调用这个工具（比如主 Agent 尝试调用 subagent_only 域的工具，会被拦截并抛 ToolExecutionError）。这是"第二道防线"——第一道是注入阶段（VisibilityCalculator 保证不可见工具根本不注入给模型），第二道是执行阶段（即使模型通过某种方式输出了不可见工具名，执行前也会被拦）。纵深防御，防止 prompt 注入或模型幻觉绕过。

**Q2-9：-43.4% / -45.2% / 100% 这几个指标怎么测的？**

> **标准回答**：`scripts/benchmark_tools.py` 静态模式，33 个场景（覆盖 5 个 Skill、主/子两种角色，含"你好，自我介绍"这种无工具场景和"算 3*7"这种对抗用例）。每个场景用**规则意图识别**模拟 Skill 激活，然后对比两套注入：全量注入（baseline，忽略执行域隔离，所有非 internal 工具都注入）vs 执行域隔离（按激活 Skill 计算可见集）。指标：可见工具数均值 6 → 3.39（-43.4%）；Schema Token 用"schema 字符数 / 4"估算，504 → 276.24（-45.2%）；FC 准确率 = 33 个场景中"预期工具在隔离后的可见集中"的比例，100%。**注意口径**：这个 FC 是静态代理指标（工具可达性），不是真实 LLM 调用的正确率，真实模式需要 LLM Key 跑完整工具循环统计，测试文档我写在了 docs/tests/指标测试-工具治理.md。

**Q2-10：为什么自研 BaseTool 而不用 LangChain 的 BaseTool？**

> **标准回答**：我对比过。LangChain 的 BaseTool 功能全但重，它的生命周期、回调、错误处理跟我的需求有错位：我需要的是**极简抽象**——name、description、domain（执行域）、requires（依赖声明）、input_schema（JSON Schema）、async execute。四个理由：第一，执行域隔离需要 domain 字段，LangChain 的工具模型没有这个概念，硬套要 hack；第二，依赖解析需要 requires 字段做拓扑，LangChain 没有；第三，注入格式要转成 OpenAI function-calling 给 bind_tools，自研 schema 转起来干净；第四，测试和 mock 简单。所以我的 BaseTool 是自研的轻量 ABC（借鉴 LangChain 设计），而 LLM 接入和 bind_tools 仍然用 LangChain——**各取所长：框架管模型接入，自研管工具语义**。这是我在"简历修正建议"里建议你如实说明的点，面试官问起就说"借鉴 LangChain 抽象但为执行域隔离自研了轻量工具模型"。

**Q2-11：内置工具有哪些？分别在哪个域？**

> **标准回答**：7 个内置工具：calculator、retrieval_tool、memory_tool 是 direct 域（恒可见）；file_read_tool、file_write_tool、file_list_tool 是 skill_only 域（随 data_analysis / document_summary 等 Skill 激活）；search_tool 是 subagent_only 域（只给子 Agent 用）。internal 域目前**没有实际工具**——机制和常量都定义好了（HIDDEN_DOMAINS），但内置工具里没有 internal 实例，我留了扩展位：比如"记忆管理工具"这类系统内部调用、不该暴露给模型的功能，未来放进去。

**Q2-12：工具调用失败怎么处理？**

> **标准回答**：两层：执行层——工具抛出异常时 ToolOrchestrator 捕获并转成 ToolCallRecord(success=False, error=...)，把错误信息回填给 LLM 让它决定下一步（换参数重试、换工具、或直接回答），**不会中断整个循环**；持久层——失败记录照常落库审计。MCP 远程工具失败同理，见第 6 章。

**Q2-13：这个项目的工具数量怎么控制？会不会无限膨胀？**

> **标准回答**：三个机制：第一，**执行域隔离**——工具再多，单次注入的可见集只跟激活 Skill 相关，这是"横向膨胀"的对冲；第二，**MCP allow_tools 白名单**——接入远程 MCP 服务器时，如果 allow_tools 非空，只注册白名单内的工具，防止第三方 server 把整个工具清单灌进来（这是"纵向膨胀"的对冲）；第三，**Schema 精简**——工具的 description 和参数描述是 token 大头，设计工具时约束描述长度。另外实测数据就是证明：全量 6 个工具注入 504 token，隔离后 3.39 个 / 276 token，单次调用的 prompt 成本明显下降。

### 2.2 工具治理方向的技术八股

**Q2-B1：Function Calling 的原理是什么？**

> **标准回答**：Function Calling（工具调用）是模型能力 + 协议配合：开发者在请求里附加工具定义（JSON Schema），模型在推理时如果判断需要调用工具，就输出一个**结构化的工具调用对象**（工具名 + 符合 Schema 的参数 JSON），而不是自然语言。调用方（Agent 框架）执行工具，把结果作为新的消息回传给模型，模型基于结果继续推理或给出最终回答。关键是：模型不执行工具，只"决定并声明"调用，执行权在 Agent 侧——这保证了安全边界和可审计。OpenAI 是这一范式的开创者，OpenAI-compatible 的模型（我项目用的 DeepSeek / 百炼）都支持 bind_tools。

**Q2-B2：JSON Schema 是什么？为什么要给工具写 Schema？**

> **标准回答**：JSON Schema 是描述 JSON 数据结构的规范（字段名、类型、必填、枚举、描述），工具 Schema 告诉模型"这个工具有什么参数、每个参数什么含义、怎么传"，模型据此生成合法的调用参数。Schema 质量直接影响 FC 准确率：description 写得清楚，模型才知道什么时候该用这个工具、参数怎么填。

**Q2-B3：拓扑排序是什么？除了工具依赖还用在哪些场景？**

> **标准回答**：拓扑排序是有向无环图（DAG）的线性排序，保证每条边 u→v，u 都排在 v 前。用在：构建工具链（本项目的 Skill/工具依赖）、编译器的依赖构建顺序、包管理器安装顺序、任务调度（有依赖的任务执行顺序）。Kahn 算法（入度表 + 队列）和 DFS 都可以实现。

**Q2-B4：工具注入的 prompt 是怎么组织的？会不会有 Lost in the Middle 问题？**

> **标准回答**：工具定义通过 bind_tools 附加在请求的工具参数区，不占用对话文本；描述里把"何时用、何时不用"写清楚（决策规则）。Lost in the Middle（长上下文中间部分被模型忽略）是通用问题，缓解手段：关键规则放首尾、工具描述精炼、控制可见工具数量——我的执行域隔离本身就在减小工具列表长度，是天然缓解。

## 3. 简历第 3 条：混合检索（向量 + BM25 + RRF + 精排）

**简历原文**：混合检索：基于 Milvus + BM25 双路召回、RRF 融合、跨文档一跳扩展与本地精排。50 条标注查询实测 Recall@10 33.6%、MRR 0.68（跨文档查询 0.87）；向量服务异常自动降级本地 BM25，不中断对话。

### 3.1 项目深挖 Q&A

**Q3-1：为什么做混合检索？纯向量检索有什么问题？**

> **标准回答**：纯向量检索有两个典型问题：第一，**关键词/精确匹配不敏感**——用户搜"RFC 7231"或"SLA 编号"这种精确标识，向量检索可能召回语义相关但没包含该编号的文档；第二，**专业术语和专有名词召回差**——产品名、人名、缩写（K8s HPA 这种）的向量表示与口语描述距离远。反过来纯 BM25 无法理解语义同义（"年假制度"在 HR 文档里可能写作"休假规则"）。所以双路互补：**向量路解决语义同义，BM25 路解决精确词与编号**，融合后一路不足时另一路保底。这是 RAG 面试的共识答案，我在项目里落地验证过。

**Q3-2：BM25 的原理？跟 TF-IDF 什么关系？**

> **标准回答**：BM25 是 TF-IDF 的进阶版，对每个词算一个权重分数再加总：它把 TF 做了**饱和处理**（`tf / (tf + k1*(1-b+b*dl/avgdl))`，防止高频词主导），把 IDF 用平滑公式（`log(1 + (N - df + 0.5)/(df + 0.5))`）处理，还有**文档长度归一化**（参数 b 控制）。k1 和 b 是经验参数（k1 默认 1.2-2.0，b 默认 0.75）。我用 rank-bm25 库的 BM25Okapi。中文分词这块是个工程点：英文按空格/标点切分小写，中文按**单字符切分**（CJK 正则），因为小语料下用 jieba 分词反而引入词典误差，单字切分简单可靠。

**Q3-3：为什么用 RRF 融合，不用加权分数相加？**

> **标准回答**：RRF（Reciprocal Rank Fusion）的公式是 `score(d) = Σ 1/(k + rank_i(d))`——**只看排名不看原始分数**。加权相加需要把向量相似度和 BM25 分数放到同一量纲，但这两路的分数分布完全不同（一个余弦/IP 值、一个是词频统计值），权重很难调且不稳定；RRF 天然跨路可比：每路只贡献"排名信息"，k=60 是经典平滑参数（防止排名靠前的分数过大、以及处理并列排名）。实测我们的 50 条查询 RRF 融合效果稳定，参数也基本不用调。

**Q3-4：向量召回、BM25、reranker 三者的关系？为什么精排是二次阶段？**

> **标准回答**：召回阶段要"广"——向量和 BM25 双路各取 top_k（我取 10）召回候选，RRF 融合；精排阶段要"准"——召回出的候选可能几十条，用 reranker 对 (query, chunk) 逐对打分重新排序取 top_n。为什么要分开：**召回模型（双塔/bi-encoder）快但粗**，query 和 doc 分别编码算相似度，适合海量候选粗筛；**精排模型（cross-encoder）慢但准**，query 和 doc 拼接一起过编码器，能看到词级交互。所以经典做法是"粗召回 + 精排"两级，成本可控、精度更高。我项目里 reranker 默认走 API（阿里云百炼 qwen3-rerank），本地 provider 用 sentence-transformers 的 CrossEncoder，可切换。

**Q3-5：索引怎么建的？向量和 BM25 双写怎么保证一致性？**

> **标准回答**：离线索引在 `retrieval/pipeline.py`：文档上传后 → 解析（PDF/docx/md/txt）→ 分块（递归字符分块，默认 512 字符 / 64 重叠）→ 向量化 → 同时写 Milvus（向量）和 BM25Store（内存索引）+ PG 的 chunks 表。BM25 索引是**进程内内存索引**（rank-bm25 的 BM25Okapi 对象），启动时从 chunks 表全量重建，增量时 add/add_batch 重建整个对象（当前语料量级可接受）。一致性：以 PG chunks 表为**单一事实源**，重建时三处同步。已知限制：BM25 内存索引**跨进程不共享**——API 与 Worker 是两个进程，各自有各自的 BM25 索引，多进程部署下知识检索主要由 Milvus 向量路召回，这是文档里标注的已知限制。

**Q3-6：Milvus 为什么选它？HNSW 参数怎么配的？**

> **标准回答**：选 Milvus 的理由：**独立服务的向量数据库**，支持持久化、多副本、分布式扩展（对比 FAISS 只是进程内库，不支持分布式）；云原生部署（docker-compose 一键起），HNSW 索引成熟。项目里 collection 是 knowflow_chunks，向量维度 1024（qwen3.7-text-embedding 默认），索引 HNSW（M=16, efConstruction=200），度量方式 IP（内积），搜索时 ef=64。HNSW 是"跳表 + 图"的思想：每层是近似近邻图，高层稀疏、低层稠密，搜索从高层贪心下降到低层，复杂度 O(log n) 级别，ef 控制搜索宽度（越大越准越慢）。

**Q3-7：Recall@10 33.6%、MRR 0.68 具体怎么测的？**

> **标准回答**：`eval/scripts/compare_baseline.py` 的 GraphRAG vs Hybrid 对比评测：**50 条人工标注查询**（直接查询 15 条、跨文档查询 20 条、语义查询 15 条），语料是 5 篇模拟企业文档 43 个分块（财务、HR、IT、运维、产品手册），静态模式（hashing embedding + 词项重叠精排）跑完整引擎链路。判定口径是**文档级展开**：评测集标注 relevant_doc_ids，相关 chunk = 该文档的全部 chunk，所以 Recall 数值整体偏低。结果：Hybrid Recall@10 33.6%、MRR 0.6592，精排后 MRR 0.6804（≈简历的 0.68）；跨文档场景 Hybrid MRR 0.80、GraphRAG（带一跳扩展）MRR 0.8667（≈简历的 0.87）。**诚实说明**：这是静态口径，embedding 不是真实模型，真实模型链路要按 docs/tests/指标测试-检索.md 跑。

**Q3-8：为什么 Recall@10 只有 33.6%？是不是太低了？**

> **标准回答**：三个原因，都是口径问题不是实现 bug：第一，**文档级判定口径**——一条查询只要没召回"相关文档的全部 chunk"就算漏，43 个 chunk 里一个文档就 7-10 个 chunk，top-10 很难全覆盖，Recall 天然低；第二，**hashing embedding**——静态模式为了可复现用假 embedding，语义能力弱；第三，**合成语料**——5 篇文档构建的评测集，非真实企业数据。换个角度：同样是这套评测，最新的 run_eval 用 **chunk 级判定**（相关 chunk 是具体标注的块），Recall@10 是 23%、MRR 21.83%——两套数字都是真的，差异完全来自"相关 chunk 怎么判定"。**面试官如果揪这个数字，主动讲清楚判定口径 + 诚实说目标 +8% 未达成（实测 -1.0%），但跨文档场景 GraphRAG 的 MRR 是实打实提升的（0.80→0.87）**。这也是为什么我强调"评测口径比数字本身更重要"。

**Q3-9：跨文档一跳扩展（expander）现在还在代码里吗？**

> **标准回答**（诚实回答，必须背）：**现在不在**。V1 阶段我实现了 GraphRAG 风格的一跳扩展：索引后对同名实体做跨文档链接（same_as 关系），检索命中一个 chunk 后，通过实体链接找到共享该实体的其他文档 chunk，实现"跨文档一跳扩展"（compare_20260608.md 里 GraphRAG 的数据就是带扩展的，跨文档 MRR 0.80→0.87 的正向收益来自它）。但后来一次重构（commit 92b792b，"移除 PostgreSQL 图谱检索"）中，因为 PG 图谱存储（实体表、关系表、graph_repo）对当时的问题域偏重，我把实体抽取、图谱存储、扩展器一并移除了，检索链路收敛为 **hybrid → rerank → cache**。代价就是"跨文档一跳扩展"这个能力暂时下线，代码里只剩 ChunkScore.source 注释和 openapi 的 with_expand 参数的陈旧描述。**这个必须主动坦白**，简历上"跨文档一跳扩展"建议改成演进史表述（见第 0 章）。

**Q3-10：向量服务异常时怎么降级？"自动降级本地 BM25 不中断对话"是怎么实现的？**

> **标准回答**（诚实回答）：**当前实现是"半降级"**：embedding 服务异常时 `embed_one(query)` 返回空向量，HybridSearch 检测到 query_vec 为空就跳过向量路，只走 BM25 关键词路，检索不中断——这部分是真实落地的；但 Milvus 本身抛异常（连接断了）时，当前代码没有 try/except 包裹，会向上抛，属于"显式暴露问题"而不是"降级"。所以简历"向量服务异常自动降级本地 BM25"严格讲只对了一半。完整的"Milvus 挂了自动降级 BM25 + 告警"是设计意图，我在 docs/tests/指标测试-检索.md 里写了完整降级验收，代码层还没做完。另外三个旁路降级是真实存在的：检索缓存 Redis 不可用 → no-op 不阻塞；文档标题获取失败 → warning 不阻塞；query 改写 LLM 失败 → 回退原 query。

**Q3-11：检索缓存怎么做？**

> **标准回答**：`retrieval/cache.py` 的 RetrievalCache，用 Redis 存 (query 归一化后的 key → 检索结果)，TTL 300 秒，命中直接返回省掉双路召回 + 精排的开销；Redis 不可用或操作失败时 no-op + warning，不阻塞检索。key 是查询文本归一化（去空格/小写）后的哈希，避免重复检索同样的查询。

**Q3-12：Query 改写（rewriter）做什么？**

> **标准回答**：`retrieval/query_rewriter.py`：多轮对话里用户可能说"那它的审批流程呢？"——"它"指代前文的某个系统。改写器用 LLM 结合历史把 query 补全成自包含的查询（指代消解），再拿去检索；改写失败或没历史就原样返回，不影响主流程。这是检索前增强（Advanced RAG 的 pre-retrieval 环节）。

**Q3-13：分块策略为什么是 512/64？**

> **标准回答**：递归字符分块，512 字符主块 + 64 重叠。权衡：小块检索精度高但上下文易断裂，大块上下文完整但噪声多、token 贵；512/64 是常见经验值（200-500 token 区间 + 10-20% 重叠），且 chunk 语义相对完整。参数都在配置里（chunk_size / chunk_overlap），可以用检索指标做 A/B 调优——这是已知的优化点（semantic chunking、父子块索引都是备选）。

### 3.2 检索方向的技术八股

**Q3-B1：Recall@K、Precision@K、MRR、NDCG 分别是什么？RAG 里最看重哪个？**

> **标准回答**：Recall@K = top-K 中相关文档数 / 总相关文档数，回答"找得全不全"；Precision@K = top-K 中相关文档数 / K，回答"找得准不准"；MRR（平均倒数排名）= 第一个相关文档排位的倒数取平均，回答"第一个对的排多靠前"；NDCG = 按位置加权的归一化累计增益，排位越靠前增益越大，回答"排序质量"。**RAG 里 Recall@K 是底线指标**——生成模型只能基于检索到的内容回答，没召回正确答案，生成再强也是零；MRR/NDCG 反映排序质量，影响"注入的上下文是否被噪声稀释"。

**Q3-B2：余弦相似度、内积、欧氏距离的区别？**

> **标准回答**：余弦只看**方向夹角**（归一化后=内积），对向量长度不敏感，是文本相似度最常用；内积（IP）未归一化时同时反映方向和模长，Milvus 用 IP 通常配合归一化向量（归一化后 IP == 余弦）；欧氏距离看绝对距离，对模长敏感，适合特征本身有量纲意义的场景。文本 embedding 通常归一化，所以三者在一定条件下等价。

**Q3-B3：HNSW 的原理？为什么召回快？**

> **标准回答**：HNSW（分层可导航小世界图）：多层图结构，**上层图稀疏（长程连接）用于快速定位，下层图稠密（短程连接）用于精确查找**，类似跳表 + 小世界的结合。搜索从最高层开始，贪心选择邻居中距离最近的节点，逐层下降到最底层；因为高层一跳能跨越很远，所以"先粗定位再精查找"，复杂度接近 O(log n)。参数：M（每层最大连接数）、efConstruction（建图搜索宽度）、ef（查询搜索宽度，越大越准越慢）。相比 IVF（先聚类分区再查，召回可能漏掉分区边界附近的点），HNSW 召回质量更高、无"边界遗漏"问题。

**Q3-B4：什么是 embedding？好的 embedding 模型怎么选？**

> **标准回答**：embedding 是把文本映射为稠密向量的表示学习，语义相近的文本向量距离近。选型维度：语言支持（中文场景 bge、m3e、gte 系列）、维度（高维精度好但成本高）、最大输入长度（影响分块策略）、推理速度与成本。评估用 MTEB 基准 + 自己领域的测试集（通用榜单冠军在垂直领域未必最优）。对称/非对称：query 短、doc 长时用非对称模型（E5 系）。我项目默认走阿里云百炼 qwen3.7-text-embedding API，本地可切 SentenceTransformer。

**Q3-B5：RAG 的演进路线（Naive → Advanced → Modular）？**

> **标准回答**：Naive RAG 是"检索 → 拼接 → 生成"的最简链路，问题：检索质量不稳、上下文割裂、幻觉率高；Advanced RAG 在检索前/中/后都做优化——检索前（query 改写、HyDE、多查询扩展）、检索中（混合检索、多路召回、元数据过滤）、检索后（rerank、上下文压缩）；Modular RAG 把各环节拆成可插拔模块，按场景组装不同 pipeline（简单问题走轻量链路、复杂问题走完整链路）。我项目实际是 Advanced RAG（query 改写 + 混合检索 + rerank），路由/模块化是 Modular 的雏形（understand 意图分类决定走哪条链路）。

**Q3-B6：什么是 Lost in the Middle？怎么缓解？**

> **标准回答**：Stanford 2023 的研究：LLM 对长上下文中间部分关注度低于首尾，答案在中间时准确率下降。缓解：把最相关的文档放首尾或按相关性交替排列、减少注入文档数（top-3 而非 top-10）、map-reduce 逐文档提取再合并、上下文压缩、用长上下文友好的模型。

**Q3-B7：RAG 的评测分哪两层？**

> **标准回答**：检索层（Recall@K、MRR、NDCG）+ 生成层（Faithfulness 忠实性、Answer Relevance 相关性、Context Precision/Recall）。工具如 RAGAS。生成层评估是难点，通常要构建 golden test set（带标注的 QA 对）做回归。我项目 eval/ 里有统一的 run_eval.py 入口，静态模式覆盖检索层三项指标 + QA 要点命中率 + 工具 FC 准确率。

## 4. 简历第 4 条：记忆管理（四级管线）

**简历原文**：记忆管理：基于 Redis + PostgreSQL 实现"短期→重要性筛选→压缩→长期"四级管线，每 5 轮自动沉淀，语义去重、冲突检测留痕待审不阻断写入，长会话关键信息不丢失。

### 4.1 项目深挖 Q&A

**Q4-1：记忆管线为什么分四层？各层职责是什么？**

> **标准回答**：对应记忆的"生命周期"：**短期层（Redis）**——会话级即时记忆，消息实时写入 Redis List（key `mem:short:{session_id}`，TTL 3600 秒），快、天然带过期；**重要性筛选**——不是所有消息都值得进长期记忆，用重要性打分（LLM 输出 0-10 分，失败回退规则打分）过滤，阈值 6.0 以上才沉淀，只筛选 user 消息（偏好/习惯由用户表达）；**压缩**——Compressor 用 LLM 把多条高价值消息压缩成摘要（保留偏好与事实），失败回退"每条截断 200 字符拼接"；**长期层（PG）**——持久化到 long_term_memories 表，按用户隔离，带 embedding 支持向量召回。为什么分层：**热数据放内存（Redis），冷数据落磁盘（PG），符合访问模式**，这是设计文档 D5 决策（ADR）。

**Q4-2：重要性打分怎么做？为什么 LLM + 规则双轨？**

> **标准回答**：`memory/importance.py` 的 ImportanceScorer：主路径让 LLM 输出 0-10 的整数重要性 JSON；**LLM 缺失或失败时回退规则打分**——高置信关键词（如"我偏好/我习惯/记住"）9.0 分，中置信 6.0，默认 2.0，长消息（>100 字）+1.0 封顶 10。为什么双轨：LLM 打分准但可能失败/超时/花钱，规则兜底保证"沉淀"这条关键路径永远能跑；这体现了我"关键路径必须有降级"的工程习惯。设置里 `memory_sediment_threshold=6.0`。

**Q4-3：每 5 轮自动沉淀怎么触发？**

> **标准回答**：在 chat_service 的 `_observe_and_sediment`：每条 assistant 消息落库后，统计当前会话轮次数，`MemoryManager.should_sediment(turns, interval=5)`——轮次数是 5 的倍数就触发 sediment（间隔是配置项 `memory_sediment_interval=5`）。sediment 流程：取短期记忆最近最多 100 条 → 筛 user 消息且重要性 ≥ 6.0 → 压缩 → 逐条写长期记忆 + 蒸馏会话摘要 → 清空短期（防止重复沉淀）。沉淀与 DB 事务同批提交，不额外增加事务。

**Q4-4：语义去重怎么做？**

> **标准回答**：`memory/long_term.py` 的 `_find_duplicate`：新记忆先用 embedding 与用户存量记忆算**余弦相似度**，相似度 ≥ 0.9（`memory_dedup_threshold`）判定为重复，处理方式是**覆盖更新**——内容取新的、importance 取较大值，防止冗余堆叠；无 embedding 时用 difflib 的 SequenceMatcher 文本相似度兜底。0.9 阈值是刻意收紧的（宁可少去重也不误删有差异的记忆）。

**Q4-5：冲突检测怎么做？"留痕待审不阻断写入"是什么意思？**

> **标准回答**：`memory/conflict.py` 的 ConflictDetector 是**纯启发式、无 LLM**：两类冲突——"态度反转"（主题文本相似度 ≥ 0.3 且否定极性相反，比如"我喜欢远程办公" vs "我不喜欢远程办公"）和"数值不一致"（主题相似且数值集合不同，比如"年假 5 天" vs "年假 10 天"）。检测到冲突写入 `memory_conflicts` 表留痕（status=pending，待人工/后续审核），但**新记忆照常写入，不阻断**——因为"等待审核"不应该阻塞记忆管线的正常工作。这是"审计优先"的设计：宁可多记一条可能矛盾的，也不能丢信息，矛盾留给审核环节处理。

**Q4-6：长期记忆怎么召回？分数公式是什么？**

> **标准回答**：`memory/recall.py` 的 LongTermRecaller，在 Python 内做余弦相似度召回（PG 没装 pgvector 扩展，embedding 以 JSON 序列化二进制存 LargeBinary 字段）。召回分数公式：`score = 0.7 × 余弦相似度 + 0.2 × (importance/10) + 0.1 × 1/(1 + 距上次召回天数/7)`——三个维度：**相关性为主（0.7）、重要性其次（0.2）、时效性兜底（0.1）**，召回后更新 last_recall 时间戳（"用进废退"）。默认 `memory_recall_top_k=3`。召回结果 + 最新会话摘要（蒸馏的核心记忆，前缀"核心记忆:"）一起注入系统提示。

**Q4-7：为什么不用 pgvector，而在 Python 里算余弦？**

> **标准回答**（诚实回答）：PG 当时没启用 pgvector 扩展（迁移和运维成本），MVP 阶段记忆条数少（每条用户几十到几百条），Python 里全量算余弦完全扛得住，代码还简单可测。这是明确的"当前规模下的取舍"：**记忆量大了之后要换 pgvector 或 Milvus 做向量召回**，我已在改进清单里。面试官问规模必要性时，这就是标准答案——"我知道这是单机小规模方案，规模化方案是 pgvector/专用向量库"。

**Q4-8：记忆的"蒸馏"是什么？**

> **标准回答**：sediment 时压缩出的摘要不只作为单条记忆，还会 `save_summary` 写成**会话级核心记忆**（memory_summaries 表），recall 时以"核心记忆:"前缀注入。这是"长期记忆的浓缩"：命中条目给细节，核心摘要给"这个人最重要的画像"，两层配合，避免只召回碎片化的单条记忆。

### 4.2 记忆方向的技术八股

**Q4-B1：Redis 有哪些数据结构？你项目里用了哪些？**

> **标准回答**：String（缓存/计数）、List（消息队列/列表）、Hash（对象字段）、Set（去重/标签）、ZSet（排行榜/有序集合，score 可做权重）、Stream（消息队列，5.0+）。我项目：短期记忆用 **List**（rpush 追加消息、lrange 取最近 N 条）；检索缓存用 String（key→序列化结果 JSON）；**任务队列用 Redis Stream**（XADD/XREADGROUP/XACK，消费组 + 重试 + DLQ，见第 7 章）。

**Q4-B2：Redis 的过期删除和内存淘汰策略？**

> **标准回答**：过期删除：惰性删除（访问时检查过期）+ 定期删除（每秒抽查部分 key）；内存淘汰：maxmemory-policy 八种，常用 allkeys-lru / volatile-lru / allkeys-lfu，企业常用 allkeys-lru。我项目短期记忆 TTL 3600 秒，靠过期自动清理会话级记忆。

**Q4-B3：Redis 持久化 RDB 和 AOF 的区别？**

> **标准回答**：RDB 是定期全量快照（fork 子进程写二进制 dump），恢复快但有丢失窗口（两次快照间的数据）；AOF 是追加写命令日志（可配 everysec/always），丢失窗口小但文件大、恢复慢；4.0+ 有 AOF rewrite 和混合持久化。我项目短期记忆和缓存**不需要持久化**（丢了可重建），任务队列的持久性靠 PG 侧落库兜底——这是"按数据重要性选持久化级别"的思路。

**Q4-B4：什么是向量相似度检索？余弦相似度的计算复杂度？**

> **标准回答**：文本 → embedding 向量 → 用余弦/内积/欧氏算距离，返回最相似的 top-K。余弦复杂度：两向量点积 O(d)（d 是维度，我项目 1024），暴力全量比对 O(N×d)。所以条数多了必须用 ANN 索引（HNSW/IVF）或向量数据库，不能暴力算。

**Q4-B5：长期记忆和"对话历史"有什么区别？**

> **标准回答**：对话历史是**原始的逐轮消息**，用于当前会话的上下文（量大、原始、带时序）；长期记忆是**从历史中提炼的持久知识**（用户偏好、事实、结论），跨会话复用、按重要性筛选、去重压缩过。原始历史进不了上下文就过期，记忆是"信息的中长期沉淀层"。对应到项目：历史走 context 模块的窗口/摘要，记忆走 memory 管线的四级沉淀。

### 4.3 追问链

| 追问 | 应对要点 |
|---|---|
| "重要性打分是 LLM 打分，那打分本身就花 token 啊？" | 只在沉淀时（每 5 轮）对候选消息打分，频率低、量小；规则兜底省 token |
| "记忆冲突留痕了，谁来审？" | 当前是 pending 状态 + 日志告警，审核动作是待办（API/后台人工审核），可讲清楚这是 MVP 取舍 |
| "用户删了会话，记忆还在吗？" | 长期记忆按 user_id 隔离存储，不随会话删除；会话删除只清短期（Redis TTL/显式删除） |
| "多用户记忆怎么隔离？" | 长期记忆表带 user_id，召回按 user_id 过滤；短期 key 带 session_id |
| "如果重做记忆，改什么？" | 加分：pgvector 化召回；LLM 冲突检测（启发式误报多）；记忆重要性随时间衰减（EWC/时效权重）；记忆条目拆分（一条记忆一个原子事实） |

### 4.4 改进点

> **标准回答**：1) 长期记忆向量化存储（pgvector/Milvus），当前 Python 全量余弦只适合小规模；2) 冲突检测升级为 LLM 语义级（当前启发式只覆盖态度反转和数值不一致）；3) 记忆重要性随时间和使用频率衰减；4) 记忆可解释性——每条记忆可溯源到原始对话；5) 提供记忆编辑/删除的审核闭环。

## 5. 简历第 5 条：长会话上下文治理（Token 预算 + 卸载）

**简历原文**：长会话上下文治理：按 Token 预算分级裁剪上下文，超长工具结果卸载至沙盒、仅注入引用且可经工具读回，召回与写入分离、整理异步化，上下文不随会话无限膨胀。

### 5.1 项目深挖 Q&A

**Q5-1：上下文预算怎么分配的？**

> **标准回答**：总预算默认 32000 token（`context_budget_tokens`），按模块配额分配（`context/budget.py` 的 BUDGET_RATIOS）：system 10% / history 35% / tools 20% / retrieval 25% / memory 10%。这样任何单个模块爆掉都不会吃光整个窗口，保证各模块都有空间。

**Q5-2：超预算的处理顺序是什么？**

> **标准回答**：`ContextStrategy.process` 按 **窗口 → 摘要 → 卸载 → 截断** 四级处理：第一步，历史先过**滑动窗口**（`window_max_turns=20` 轮，每轮 user+assistant 两条），超 budget 的旧历史被裁掉；第二步，窗口裁完仍超 history 配额 → **LLM 摘要替代**（Summarizer 把历史压成摘要，进 system_extra，历史清空）；第三步，**长文本（检索/工具结果）**超阈值 → **卸载到沙盒**（Spiller，阈值 `spill_threshold_tokens=4000`），只注入引用；第四步，仍未收敛的模块**截断保留前缀**并标记（`truncate:{module}`）。每一步动作都记录进 ContextStats.actions，供 Trace 展示——**面试官能从这个设计看出"不是一刀切截断，而是先保语义再保长度"**。

**Q5-3：卸载（spill）具体怎么实现？**

> **标准回答**：`context/spiller.py` 的 Spiller：文本 token 数超过 4000 时，写入**会话沙盒**的 `sessions/{sid}/workspace/spilled/{时间戳}.txt`（后端是 MinIO，不是本地文件系统——ADR 0007 的决策：对象存储天然隔离、无宿主文件系统越权风险、支持配额和 TTL），然后**引用替换**：原文替换成 `{"spilled": true, "path": "/workspace/..."}` 引用对象注入 LLM。关键设计：**只丢"上下文占用"，不丢"数据"**——用户后续说"把刚才那份数据存成 CSV"，模型可以通过 file_read_tool 按引用路径把原文读回来。这是"长上下文不截断，而是挪到可读回的地方"的完整闭环。

**Q5-4：为什么卸载到 MinIO 而不是本地文件系统？**

> **标准回答**：ADR 0007 的决策，四个理由：**隔离性**——每个会话独立的 bucket prefix/虚拟路径，天然按会话隔离，没有宿主文件系统越权风险；**路径安全**——沙盒层做了路径校验（拦截 `../`、绝对路径、跨会话访问）；**配额与生命周期**——默认 100MB 配额 + TTL 清理，MinIO 支持对象生命周期规则；**一致性**——文件读写经统一 WorkspaceManager 接口，与未来多实例部署兼容（本地文件系统多实例就裂了）。

**Q5-5：上下文管理在链路里哪个环节生效？**

> **标准回答**：直连链路里，chat_service 的 `_build_context_messages` 会优先走 ContextManager.build：传入 query、历史、检索上下文、记忆、工具结果，ContextManager 内部 = ContextStrategy（策略处理）+ ContextBuilder（组装 messages），输出可直接注入 LLM 的 messages + 处理统计（ContextStats）。工具编排链路里，工具的中间结果在 ToolOrchestrator 内管理。所以上下文治理是**可插拔的一层**——注入 ContextManager 就走完整策略，不注入就用内置简化组装，测试友好。

**Q5-6："召回与写入分离、整理异步化"这个简历点怎么讲？**

> **标准回答**（诚实回答）：**当前代码没有独立的"召回与写入分离 / 上下文整理异步化"模块**——检索结果缓存的写入是同步 await，上下文整理也是同步的。真实的"异步化"落地在另外两处：**报告生成**（ReportService 用 asyncio.create_task 后台生成，不阻塞用户）和 **SSE 流式中的事件桥接**（编排器的回调事件经 asyncio.Queue 异步消费转发）。所以这个简历点要么删掉，要么按"设计导向、代码部分落地"来回答，千万别硬编。我会在改进点里讲清楚"上下文整理后台异步化"是计划内的事。

**Q5-7：Token 计数怎么做的？**

> **标准回答**：`context/token_counter.py`：优先用 tiktoken 按模型编码精确计数（`tiktoken.encoding_for_model`），失败回退"字符数 / 4"估算。tiktoken 是 OpenAI 的 BPE tokenizer 库，模型对应编码器；回退估算保证任何环境下 token 计数都不会抛异常。

### 5.2 上下文方向的技术八股

**Q5-B1：什么是上下文窗口？模型上下文不够怎么办？**

> **标准回答**：上下文窗口是模型单次请求能处理的 token 上限。超限的后果：要么报错，要么静默截断（尾部）。治理手段分层：**窗口管理**（滑动窗口只留最近 N 轮）、**摘要压缩**（历史压成摘要）、**检索过滤**（只注入 top-K 相关片段）、**上下文压缩**（LLMLingua 这类工具做 token 级压缩）、**外部存储**（卸载到文件/数据库，引用读回——我项目的做法）。设计原则：**长会话的核心不是"塞更多"，而是"留最相关"**。

**Q5-B2：什么是 Lost in the Middle？（第 3 章已背，这里是补充）**

> **标准回答**：见第 3 章 Q3-B6。上下文治理里对抗它的手段：最相关内容放首尾、减少注入条数、按相关性排序注入。

**Q5-B3：tiktoken 和普通分词器有什么区别？**

> **标准回答**：tiktoken 用 BPE（Byte Pair Encoding）算法，把词拆成子词单元，覆盖任何语言的 token 切分，且与 GPT/OpenAI 兼容模型的 token 口径一致；普通分词（空格/jieba）的 token 数与模型真实计费口径不一致，会导致预算管理失准。

**Q5-B4：摘要压缩有哪些策略？**

> **标准回答**：stuff（全量塞一次总结，适合短）、map-reduce（每段单独总结再合并，省 token 但可能丢跨段信息）、refine（逐段迭代精炼，保上下文但慢）、分层摘要（先段后篇）。我项目历史摘要用的是单次 LLM 摘要（历史已在窗口内，量不大），量大了可以升级 map-reduce。

### 5.3 追问链

| 追问 | 应对要点 |
|---|---|
| "32000 是怎么定的？" | 匹配主流模型窗口（如 32K/128K 档），给检索/工具留足空间；实际按部署模型窗口调 |
| "卸载后模型说'帮我读一下那个文件'怎么办？" | 引用对象里的 path 就是沙盒虚拟路径，file_read_tool 按路径读回，闭环 |
| "截断为什么保留前缀不是保留关键部分？" | 简化 + 可预期；更优做法是保留与 query 最相关片段（可升级为智能截断） |
| "摘要替代历史，会不会丢信息？" | 会，但有取舍：摘要保留全局脉络，细节靠检索/工具按需读回；这与"卸载"共同构成完整的信息保真策略 |
| "如果重做，改什么？" | 加分：上下文整理异步化 + 落库（重会话延迟整理）；智能截断（按相关性而非前缀）；摘要缓存；工具结果分级（先摘要后卸载） |

### 5.4 改进点

> **标准回答**：1) "整理异步化"落地：会话空闲时后台整理历史/生成摘要，而不是请求路径上同步做；2) 智能截断（保留与 query 相关片段）；3) 摘要结果缓存（同会话同区间不重复摘要）；4) 工具结果分级处理（短结果直注、中结果摘要、长结果卸载）；5) 上下文预算按模型自动适配。

## 6. 简历第 6 条：MCP 工具生态接入

**简历原文**：MCP 工具生态接入：基于 MCP 2.0 SDK 实现 stdio 协议工具网关，远程工具统一适配并入注册表并自动纳入执行域隔离，内置 demo Server 独立子进程真实协议往返，连接失败自动降级告警。

### 6.1 项目深挖 Q&A

**Q6-1：MCP 是什么？协议流程是什么？**

> **标准回答**：MCP（Model Context Protocol）是 Anthropic 提出的**标准化工具/上下文接入协议**，目标是把"模型 → 工具"的对接从私有协议变成统一标准，类似"AI 界的 USB-C"。协议基于 JSON-RPC 2.0，核心流程：客户端启动 server 子进程（stdio）或连 HTTP/SSE 端点 → **initialize**（能力协商）→ **tools/list**（拉取工具清单：名称、描述、输入 Schema）→ **tools/call**（调用工具、返回结构化结果）。我项目用 MCP 2.0 SDK（`mcp>=2.0.0`），import `ClientSession`、`StdioServerParameters`、`stdio_client`。

**Q6-2：stdio 传输怎么起子进程？为什么这样设计？**

> **标准回答**：`McpGateway._connect()`：用 `stdio_client(StdioServerParameters(command, args, env))` 启动 server 子进程，读写走进程的 stdin/stdout（stdio），再包一层 `ClientSession` 并 `session.initialize()` 完成握手。每次操作（list_tools / call_tool）建立**独立连接**——子进程生命周期随连接起停，用完即清。优点：无端口、无网络暴露、进程级隔离（server 崩了不影响宿主），是本地工具的标准传输方式；缺点是每个 server 一个进程，多 server 时进程数多（可用常驻连接优化，是改进点）。超时用 `asyncio.wait_for`，默认 30 秒，防止远端 server 挂死拖死调用方。

**Q6-3：远程工具怎么适配成本地工具并入注册表？**

> **标准回答**：`tools/mcp/adapter.py` 的 `McpToolAdapter(BaseTool)`：把 MCP server 的 list_tools 结果适配成自研 BaseTool——工具名加前缀 `mcp_{server_id}_{tool_name}` 防命名冲突，描述加 `[MCP:{server_id}]` 标注来源，input_schema 透传，execute() 经 `McpGateway.call_tool` 转发。注册：`register_mcp_server(registry, server_id, command, args, domain=SKILL_ONLY, allow_tools)` 连接 + list_tools → 逐个 registry.register。**注册进 ToolRegistry 之后，自动继承整个治理体系**：VisibilityCalculator 执行域隔离、PermissionChecker 越权拦截、ToolMetrics 指标、Trace 可观测——"远程工具 = 本地工具"完全无差别。默认 domain 是 skill_only（随 Skill 激活可见），可配置覆盖。

**Q6-4：内置 demo Server 是什么？演示了什么？**

> **标准回答**：`tools/mcp/servers/demo.py` 是一个独立的 MCP server，`MCPServer(name="knowflow-demo")`，四个工具：**echo**（正常往返）、**server_time**（真实能力）、**boom**（故意抛错，验证错误处理）、**slow**（sleep 30 秒，验证调用超时降级）。以 `python -m knowflow.tools.mcp.servers.demo` 启动为**独立子进程**，走真实的 MCP stdio 协议往返。配置接入方式：`.env` 里 `KNOWFLOW_MCP_SERVERS=[{"id":"demo","command":"python","args":["-m","knowflow.tools.mcp.servers.demo"],"domain":"skill_only"}]`，启动时 lifecycle 逐个注册。这覆盖了"注册→治理→隔离→调用→降级"的完整链路演示，是我 MCP 能力面试时的 demo 材料。

**Q6-5：连接失败怎么降级？**

> **标准回答**：三层降级：**注册层**——register_mcp_server 的 list_tools 失败 → logger.warning 告警 + 返回空列表，不抛出、不阻塞其他 server 注册（单个 server 挂不影响整体启动）；**调用层**——McpToolAdapter 的 execute 失败返回 `ToolResult(success=False, error=...)`，不抛出，ToolOrchestrator 把错误回填给 LLM 决定下一步；**启动层**——lifecycle 的 `_safe_init`：dev 环境单依赖失败降级不阻塞启动，prod 严格失败即退出（环境不同策略不同）。一句话：**"连不上就告警 + 缺这个工具继续跑"**，这是工具生态接第三方 server 必备的健壮性。

**Q6-6：allow_tools 白名单是干什么的？**

> **标准回答**：控制"工具膨胀"：MCP server 可能暴露几十上百个工具，全注册进来既占注册表又稀释可见集。allow_tools 非空时，只注册白名单内的工具；这跟执行域隔离（横向裁剪）互补，做的是**接入时裁剪**（纵向裁剪）。企业接入第三方 server 时，白名单也是安全边界——只暴露需要的工具。

**Q6-7：MCP 和自定义工具协议比，优势在哪？**

> **标准回答**：**标准化 + 生态**：MCP 是开放协议，工具方写一次 server，所有兼容客户端都能用（Anthropic、各种 Agent 框架都在推）；自定义协议只能自己用，每接一个工具写一套适配。MCP 的劣势是协议是"工具清单 + 调用"的平铺模型，复杂的编排语义（依赖、权限域）要靠宿主侧自己管——所以我的设计是 **MCP 管"接入标准"，执行域隔离管"治理标准"**，两者正交组合。

**Q6-8：飞书 MCP server 是什么？**

> **标准回答**：V2 方向（ADR 0009）：自建了一个飞书 MCP server（`tools/mcp/servers/feishu/server.py`，stdio，工具 create_doc / append_to_doc / update_doc），经 httpx 直接调飞书文档 OpenAPI，目的是打通"报告生成 → 一键发布到飞书云文档"的闭环。这演示了 MCP 的两种角色：**当客户端**（接入第三方 server）和**当服务端**（对外提供 MCP server）我都有实现。

### 6.2 MCP 方向的技术八股

**Q6-B1：MCP 的传输方式有哪些？各适用什么场景？**

> **标准回答**：stdio（本地子进程，进程隔离、无网络暴露，适合本地/可信工具）和 HTTP+SSE / Streamable HTTP（远程服务，适合跨主机、多客户端共享）。本地用 stdio，远程部署用 HTTP。MCP 还支持 OAuth 认证（远程场景）。

**Q6-B2：MCP 和 Function Calling 什么关系？**

> **标准回答**：Function Calling 是"模型怎么表达工具调用"的**模型侧能力**（模型输出结构化调用）；MCP 是"Agent 怎么发现和调用工具"的**协议侧标准**（客户端 ↔ 工具服务）。两者互补：Agent 通过 MCP 发现工具、拿到 Schema，再把 Schema 绑定给模型做 Function Calling，模型输出调用后 Agent 经 MCP 转发执行。我项目就是这个组合：MCP 网关接远程工具 → 适配成 BaseTool → injector 转 OpenAI function-calling 格式 → bind_tools。

**Q6-B3：子进程管理要注意什么？（对应 stdio server）**

> **标准回答**：进程生命周期管理（启动/回收，防僵尸进程）、stdin/stdout 的字节流同步（协议帧边界）、超时与 kill（挂死要能强杀）、环境变量隔离、安全（子进程权限最小化）。我项目用 MCP SDK 的 stdio_client 封装了这些，连接退出时逆序清理（session → cm），异常路径也保证资源关闭。

**Q6-B4：JSON-RPC 是什么？**

> **标准回答**：JSON-RPC 2.0 是基于 JSON 的远程调用协议：请求带 id、method、params，响应带 id、result/error，支持通知（无响应）。MCP 的消息就建立在它之上（initialize、tools/list、tools/call 都是 method）。它是比 REST 更轻的 RPC 格式，无 HTTP 语义负担，适合进程内/子进程通信。

### 6.3 追问链

| 追问 | 应对要点 |
|---|---|
| "MCP 每次操作都重新起子进程，不慢吗？" | 连接复用是已知优化点：可维护常驻连接池/懒加载长连接；当前 MVP 优先正确性和隔离性 |
| "如果 MCP server 返回的 Schema 不标准怎么办？" | 透传 + 适配层兜底；调用时参数按 schema 校验，失败降级 |
| "第三方 server 是恶意的怎么办？" | 安全边界：allow_tools 白名单 + 执行域隔离（skill_only 需激活）+ PermissionChecker + 沙盒隔离（文件类工具只在沙盒内） |
| "MCP 生态现在还乱，你怎么看？" | 认知题：协议标准化是趋势（Anthropic/OpenAI 都在推），早期生态乱是正常阶段；我的架构把 MCP 做成可插拔接入层，协议演进不影响治理体系 |
| "如果重做 MCP 接入，改什么？" | 加分：连接复用/常驻；server 健康检查与自动重连；工具 Schema 本地缓存（省握手）；支持 HTTP 传输 |

### 6.4 改进点

> **标准回答**：1) 连接复用（常驻 session 池）；2) 工具清单本地缓存（避免每次启动重新握手）；3) 支持 Streamable HTTP 传输（远程部署）；4) server 健康检查与自动重连；5) MCP 工具的权限元数据（工具级敏感度标注，与 PermissionChecker 联动）。

## 7. 通用技术八股（面试官必考基础）

> 这一章脱离简历条目，是字节后端/Agent 岗的高频八股。每题先背"标准回答"，项目相关的题要能举出项目实例。

### 7.1 Python 核心

**Q7-1：Python 的 GIL 是什么？怎么绕过？**

> **标准回答**：GIL 是 CPython 的全局解释器锁，同一时刻只有一个线程执行字节码。多线程对 IO 密集友好（等待时释放锁），对 CPU 密集是瓶颈。绕过：多进程（multiprocessing/ProcessPoolExecutor）、C 扩展（numpy 这类释放 GIL）、异步 IO（单线程事件循环不需要并行）。我项目全链路 asyncio，模型调用和数据库都是 IO 等待，GIL 不是瓶颈；如果本地跑 embedding 推理（CPU 密集），会考虑丢进程池。

**Q7-2：装饰器是什么？实现一个带参数的装饰器？**

> **标准回答**：装饰器是接收函数、返回新函数的可调用对象，用 @ 语法糖，用于横切关注点（日志、鉴权、重试、计时）。带参数装饰器要三层嵌套：外层收参数，中层收函数，内层包装。项目里大量用 @lru_cache（缓存单例）、FastAPI 依赖注入、structlog 的日志配置都类似装饰器模式。

**Q7-3：`__init__` 和 `__new__` 的区别？单例模式怎么实现？**

> **标准回答**：`__new__` 是类方法，负责创建实例（返回实例）；`__init__` 是实例方法，负责初始化。`__new__` 在 `__init__` 前调用。单例：重写 `__new__` 保证只创建一个实例，或用模块级全局变量（Python 模块天然单例）、functools.lru_cache 装饰工厂。我项目用 @lru_cache 装饰 `get_settings()` / `get_chat_llm()` 实现配置和 LLM 客户端单例。

**Q7-4：深浅拷贝的区别？可变默认参数为什么是坑？**

> **标准回答**：浅拷贝只复制容器本身，元素共享引用；深拷贝递归复制所有内容。可变默认参数（`def f(x=[])`）的坑：默认值在**定义时创建一次**，多次调用共享同一个 list，修改会累积——正确写法是默认 None + 内部创建。项目里 dataclass 用 field(default_factory=list) 就是这个原因（见 ContextStats）。

**Q7-5：Python 垃圾回收机制？**

> **标准回答**：引用计数为主（对象引用归零立即回收），循环引用靠**分代 GC**（0/1/2 三代，对象越老扫描越少）+ 弱引用（weakref）打破循环。内存管理：小对象用内存池（pymalloc）。项目里大量异步协程和长连接，注意不要在循环中持有大对象引用。

**Q7-6：`async/await` 和 `asyncio` 的底层原理？**

> **标准回答**：async 函数是协程（可暂停可恢复），await 挂起当前协程把控制权交回事件循环；事件循环（asyncio.run 启动）维护就绪队列，IO 事件就绪时调度对应回调/协程。底层是 selectors（epoll/kqueue）多路复用。关键点：**await 之前的同步代码是阻塞的**，事件循环不切走；长时间 CPU 计算会卡住整个循环，所以 CPU 密集要丢 executor。

**Q7-7：上下文管理器（with）的实现？**

> **标准回答**：`__enter__`/`__exit__`（类实现）或 @contextlib.contextmanager（生成器实现），`__exit__` 接收异常类型/值/回溯，返回 True 吞掉异常。项目里大量使用：SQLAlchemy session、MCP 连接（asynccontextmanager 的 _connect）、文件/资源管理。

**Q7-8：`*args` 和 `**kwargs`？`__slots__` 有什么用？**

> **标准回答**：*args 收位置参数元组，**kwargs 收关键字参数字典。`__slots__` 声明允许的属性名，替代 `__dict__`，省内存（每个实例省一个 dict）、防拼写错误属性、访问更快；代价是不能动态加属性。项目里 ToolCallRecord 等高频 dataclass 可用。

**Q7-9：Python 3.13 有什么新特性？为什么项目选 3.13？**

> **标准回答**：3.13 的关键点：**JIT 编译器（实验性，提升解释器性能）**、改进的 free-threading（3.13t 实验性无 GIL）、类型参数默认值（PEP 696）、typing 增强（PEP 705）、性能整体提升（更快的解释器）。项目选 3.13 是因为它是 2024 年底发布的最新稳定版，性能提升明显，且 uv 工具链官方支持好——用新版本也体现对技术演进敏感。

### 7.2 FastAPI / Web 框架

**Q7-10：FastAPI 为什么快？依赖注入怎么工作？**

> **标准回答**：异步原生（async/await 全链路）+ Starlette 高性能 + Pydantic v2（Rust 核心，校验快）+ 自动 OpenAPI 文档。依赖注入：参数带 Depends() 时，FastAPI 按依赖图解析并注入，支持作用域（request/session 级），依赖里还能用 yield 做资源清理（get_db 返回 session 用完自动关）。项目里 api/deps.py 的 get_db、get_retriever、get_session_factory 都是依赖注入。

**Q7-11：中间件（Middleware）的执行顺序？FastAPI 中间件怎么写的？**

> **标准回答**：中间件是"洋葱模型"——请求按注册顺序进入、响应逆序返回。FastAPI 用 @app.middleware("http") 或继承 BaseHTTPMiddleware。我项目有 RateLimitMiddleware（每 IP 每分钟 60 次，超限直接返回 429，健康检查路径豁免；Redis 不可用降级放行）、Trace 注入中间件、CORS 中间件。**注意坑**：中间件里抛异常不会被 FastAPI 的 exception_handler 捕获，所以限流中间件超限直接返回 JSONResponse 而不是 raise（这是我踩过的坑，记忆里记着）。

**Q7-12：SSE 和 WebSocket 的区别？为什么项目用 SSE？**

> **标准回答**：SSE（Server-Sent Events）是 HTTP 上的**单向服务端推送**（text/event-stream），自动重连、原生 HTTP 兼容、实现轻；WebSocket 是**双向全双工**长连接。知识问答是"客户端发一问，服务端流式回一段"，单向足够——所以选 SSE（ADR 0006）：轻量、无协议升级成本、配合 nginx/网关兼容好。项目里 sse-starlette + 生产者任务 + asyncio.Queue 解耦，心跳超时只发心跳不取消业务生成器在途 await。

**Q7-13：Pydantic v2 和 v1 的区别？**

> **标准回答**：v2 核心用 Rust（pydantic-core）重写，校验快 5-50 倍；Model 配置从 class Config 改 model_config = SettingsConfigDict；`__fields__` 改 `model_fields`；新增 TypeAdapter、序列化器。项目配置用 pydantic-settings 的 BaseSettings + SettingsConfigDict(env_prefix="KNOWFLOW_")。

**Q7-14：FastAPI 的 lifespan 是什么？项目里用了什么？**

> **标准回答**：lifespan 是 ASGI 应用生命周期钩子（async context manager，启动/关闭时执行），替代废弃的 on_event。项目里 lifecycle.py：启动时初始化数据库（建表/迁移）、BM25 索引重建、MCP 工具注册（_init_mcp_tools，dev 降级 prod 严格）、Redis 等；`_safe_init` 保证单依赖失败不阻塞启动（dev）。

### 7.3 Redis

**Q7-15：Redis 为什么快？单线程模型？**

> **标准回答**：纯内存操作 + 单线程事件循环（无锁、无上下文切换开销）+ IO 多路复用（epoll）+ 高效数据结构（SDS、跳表、压缩列表/quicklist）。单线程的代价：单个慢命令（KEYS、大 key 删除）会阻塞整个实例，所以生产禁用 KEYS、用 SCAN，大 key 用 unlink 异步删。

**Q7-16：缓存穿透、击穿、雪崩是什么？怎么解决？**

> **标准回答**：穿透：查不存在的 key，请求打到 DB → 布隆过滤器或缓存空值（短 TTL）；击穿：热点 key 过期瞬间大量请求打到 DB → 互斥锁/逻辑过期（后台刷新）；雪崩：大量 key 同时过期或 Redis 宕机 → 过期时间加随机抖动、多级缓存、Redis 高可用（哨兵/集群）、熔断限流。项目里检索缓存 TTL 300s 是固定值，量大了可以加抖动。

**Q7-17：Redis 分布式锁怎么实现？有什么坑？**

> **标准回答**：SETNX + 过期时间（`SET key value NX EX ttl`），注意：value 要带唯一标识（防误删别人锁）、过期时间要够（防持锁方未完成就过期，可用看门狗续期）、释放时 Lua 脚本校验标识再删（防删错）。RedLock 有争议（时钟漂移），多数场景单机 + 合理 TTL 足够。**规模必要性**：我项目单实例部署，缓存/队列用 Redis 但分布式锁没用上——被问到就说"单实例不需要分布式锁，多实例才是前置条件"。

**Q7-18：Redis Stream 是什么？和 List 做队列的区别？**

> **标准回答**：Stream 是 Redis 5.0+ 的消息队列数据结构：XADD 追加、XREADGROUP 消费组消费（每个消息只被组内一个消费者处理）、XACK 确认、XREADGROUP BLOCK 阻塞读、PEL（pending entries list）记录未确认消息支持重投。比 List（RPOPLPUSH 手工做可靠队列）强在有消费组、ACK 机制、消息持久化。比 Kafka 轻量：无分区副本、无存储层，适合中小规模任务队列。

### 7.4 PostgreSQL / 数据库

**Q7-19：PostgreSQL 的 MVCC 原理？**

> **标准回答**：多版本并发控制：每行有 xmin/xmax（创建/删除事务 ID），读操作在快照下看到"可见版本"，写操作不覆盖旧版本而是生成新版本，因此**读写互不阻塞**。垃圾版本由 VACUUM 清理。事务隔离级别：读已提交（默认）、可重复读、可串行化。

**Q7-20：索引有哪些类型？为什么用 B+ 树？**

> **标准回答**：B+ 树（默认，范围查询友好、叶子链表）、Hash（等值查询）、GIN（全文/数组/JSON）、GiST/SP-GiST、BRIN（大表顺序数据）。B+ 树 vs B 树：数据都在叶子、叶子有序链表，范围查询一次遍历；非叶子只存 key 更矮更宽，磁盘 IO 少。

**Q7-21：SQLAlchemy 异步会话怎么管理？事务边界在哪？**

> **标准回答**：AsyncSession + async engine，会话是"工作单元"，事务边界通常在一次请求或一次服务方法内：`async with session.begin():` 或手动 commit/rollback。项目里 ChatService 每个请求一个 AsyncSession（请求级依赖注入 get_db），消息、轮次、工具调用记录在同一事务提交（`_finalize_chat` 统一 commit），保证一致性；失败 rollback 不中断 SSE（stream 里异常回滚后继续 yield error 事件）。

**Q7-22：Alembic 迁移怎么用的？**

> **标准回答**：Alembic 是 SQLAlchemy 的迁移工具：`alembic revision -m "msg"` 生成迁移脚本（upgrade/downgrade），`alembic upgrade head` 应用。项目里模型变更走迁移（如 memory_conflicts 表、长时记忆 embedding 字段），docker-compose 启动时自动迁移。

**Q7-23：连接池是什么？为什么数据库要连接池？**

> **标准回答**：连接池复用数据库连接，避免每次请求都建连/断连（TCP 握手 + 认证开销大）。异步连接池：asyncpg 自带池、psycopg_pool.AsyncConnectionPool（项目 checkpoint 用，max_size=10）、SQLAlchemy 的 pool 参数。池大小要按并发和 DB 连接上限调，太大反而拖垮 DB。

### 7.5 大模型 / LLM / Agent 通用

**Q7-24：Transformer 的 self-attention 原理？复杂度？**

> **标准回答**：Q（query）、K（key）、V（value）三个矩阵，attention 分数 = softmax(Q·Kᵀ/√d)·V——Q 和 K 的点积算相关性，√d 缩放防梯度消失，softmax 归一化，加权求和 V。复杂度 O(n²·d)（n 是序列长度）——这是长文本的瓶颈。缓解：稀疏 attention、局部窗口、线性 attention、FlashAttention（IO 优化）。ByteDance 二面常问"Agent 多轮对话里 attention 的局限"：长上下文下中间信息权重低（Lost in the Middle）、位置编码对超长序列外推弱。

**Q7-25：KV Cache 是什么？为什么能加速推理？**

> **标准回答**：生成是逐 token 自回归的，每步都要用前面所有 token 的 K/V 算 attention；KV Cache 把已算好的 K/V 缓存起来，下一步只算新 token 的 K/V 并复用缓存，避免重复计算，推理吞吐大幅提升。代价是显存占用随序列长度线性增长（有 PagedAttention/vLLM 优化）。

**Q7-26：temperature、top_p、top_k 是什么？**

> **标准回答**：temperature 控制 softmax 分布的"尖锐度"（低=确定性高，高=随机性强）；top_p（核采样）累积概率 p 之内的 token 候选池；top_k 取概率最高的 k 个。工具调用、代码、事实问答用低 temperature（0-0.2），创意生成用高。项目里 LLM 主链路 temperature 低，规划节点也用较低值保证稳定性。

**Q7-27：模型幻觉是什么？怎么治理？（必考）**

> **标准回答**：幻觉是模型生成"看似合理但无事实依据"的内容。成因：训练目标（最大似然下句）、知识截止、上下文不足/冲突。治理：**RAG 锚定外部事实 + 引用溯源 + 忠实性检查**（项目里报告链路的 ReviewRuleChecker + LLM 支持度校验 + ActiveFactChecker 就是幻觉治理）、**检索为空时允许拒答或注明"模型知识回答"**（项目系统提示第 3 条）、低 temperature、约束输出格式、Grounding 评测。**被追问"为什么 RAG 能防幻觉"**：不是消除，是"把生成锚定在可核验的证据上"，同时把"没有证据"暴露出来。

**Q7-28：RAG 和微调的区别？什么场景用哪个？**

> **标准回答**：RAG：知识可实时更新、可溯源、成本低（不训模型）、领域迁移快（换知识库即可）；微调：改变模型行为/风格/格式遵循、领域术语内化，但要标注数据 + GPU 成本、知识冻结在训练时刻。**两者不互斥**：常用组合是"微调调行为，RAG 注知识"。项目场景（企业知识问答，知识频繁更新 + 要溯源）选 RAG 为主。

**Q7-29：ReAct、CoT、Plan-and-Execute、Self-RAG、CRAG 都是什么？**

> **标准回答**：CoT（Chain-of-Thought）是"先推理后回答"的提示范式；ReAct 是"推理 + 行动"交替循环（Reasoning+Acting）；Plan-and-Execute 是"先规划后执行"；Self-RAG 让模型自省"要不要检索、检索结果有没有用、回答有没有被支持"（反射 token）；CRAG（Corrective RAG）对检索结果做可信度评估，不可信时回退联网搜索或拒答。项目里：主规划 = Plan-and-Execute，工具循环 = ReAct 式，报告调研 = 带缺口评估的迭代检索（接近 Self-RAG 的"sufficient 判定"），检索异常兜底 = 类似 CRAG 的降级思路。

**Q7-30：什么是 Agent？和 Chatbot 的本质区别？**

> **标准回答**：Agent = LLM + 规划 + 工具 + 记忆，核心是**自主决策与行动循环**：感知 → 思考 → 行动（调用工具）→ 观察 → 循环直至目标完成；Chatbot 是"输入 → 生成 → 输出"的单向问答。生产环境的关键不是"让 Agent 更自主"，而是**设计安全的自主边界**（能做什么、不能做什么、失败怎么降级）——这正是我项目工具治理和降级体系在做的事。

**Q7-31：多 Agent 架构什么时候需要？有什么风险？**

> **标准回答**：需要：任务可拆解且子任务独立（多主题调研、对比分析）、子任务可并行（收益 = 1 - 最慢/总耗时）、需要不同角色/工具权限（子 Agent 有独立工具域）。不需要：单轮问答、任务强依赖链。风险：成本放大（多倍 token）、错误传播（一个子任务错污染汇总）、失控循环、编排开销。我的设计里用"规则意图分类只对 complex 任务走多 Agent"来避免为简单问题付多 Agent 成本。

**Q7-32：怎么评测一个 Agent / RAG 系统？（必考）**

> **标准回答**：分层评测：**检索层**（Recall@K / MRR / NDCG）、**生成层**（Faithfulness / Answer Relevance / Context Precision，RAGAS 或 LLM-as-Judge）、**工具层**（FC 准确率：该调的工具是否正确调用）、**端到端**（任务完成率、人工评分、bad case 回归）。流程：构建 golden set（带标注）→ 指标脚本 → 每次迭代回归。我项目 eval/：50 条检索查询（Recall/MRR/NDCG）、60 条 QA（要点命中率）、33 个工具场景（FC 准确率），统一 run_eval.py 入口，静态模式可复现。

**Q7-33：Prompt 工程的高频技巧？**

> **标准回答**：角色定义 + 任务目标 + 输入输出格式约束 + 决策规则 + 错误处理策略 + 反例（不要做什么）；关键指令放首尾（防 Lost in the Middle）；输出用 JSON Schema 约束 + 代码侧再校验（双层约束）；Few-shot 给 2-5 个示例规范格式；工具调用描述写"何时用、参数含义"。项目里 system prompt 模板（检索为空怎么办、[n] 引用规则）、规划 prompt（注入工具清单、工具不可达不拆任务）都是这些技巧的落地。

### 7.6 消息队列 / 任务系统（对应项目异步索引）

**Q7-34：为什么不用 Celery，自封装 Redis Stream？**

> **标准回答**：三个理由：第一，**依赖少**——项目已经用 Redis，Redis Stream 5.0+ 自带消费组 + ACK + 重投机制，不需要再引入 Celery + broker + worker 框架；第二，**可控**——自封装 `tasks/broker.py`（XADD/XREADGROUP/XACK/消费组/重试 3 次/DLQ）只有几十行核心逻辑，行为完全透明，排障简单；第三，**量级匹配**——异步文档索引是中小规模任务（上传触发、worker 消费），Stream 完全够用；Celery 的重型能力（任务编排、beat、多 broker 支持）当前用不上。这是"不为没提出的需求加复杂度"的取舍，量大了再升级 Celery/消息队列，broker 接口是解耦的。

**Q7-35：任务队列怎么保证可靠？死信队列是什么？**

> **标准回答**：三个机制：**ACK**——消费者处理完才 XACK，没 ACK 的消息留在 PEL，崩溃后可重投（at-least-once 语义，配合幂等）；**重试**——失败消息重试 3 次，超过入 **DLQ（死信队列）**——DLQ 把"永远处理不了"的消息隔离出来人工排查，防止毒消息阻塞主队列；**消费组**——组内消息只被一个消费者处理，支持多 worker 横向扩展。可靠性语义是 at-least-once，所以消费者侧要有幂等（项目里索引任务按 chunk/doc 幂等设计）。

### 7.7 可观测与工程化

**Q7-36：分布式链路追踪的原理？你项目怎么做的？**

> **标准回答**：核心是 **trace_id 全链路透传 + 嵌套 span 记录时序**：入口生成 trace_id（contextvars 传播，Python 里不污染全局）、每个环节（检索/工具调用/记忆召回/Agent 决策）开 span 记录输入输出和耗时，span 带 parent 关系形成调用树。项目 observability/：Tracer（contextvars 传播 + 嵌套 Span）、SpanCollector（内存缓冲 + 批量异步落库，失败降级不阻塞主流程）、TraceStore（嵌套树查询/时间序/聚合）、Replayer（checkpoint 恢复 + 时间序事件重放，不执行 LLM 就能回放一次会话）。**这是把"黑盒 Agent"变成"可审计白盒"的关键基础设施**。

**Q7-37：你项目怎么保证代码质量？（工程化问题）**

> **标准回答**：四道门禁 + 测试体系 + 规范：**门禁**（ruff check / ruff format --check / mypy / pytest 全绿，CI PR 触发）；**测试**（771 个单测：核心算法进 tests/unit，跨模块链路进 tests/integration，SQLite 替代真实容器跑单测，覆盖率目标核心 ≥70%）；**规范**（AGENTS.md 开发规范、Conventional Commits、ADR 记录架构决策、commit-log 时间线）；**文档**（设计文档/结构文档/开发计划 + 指标测试文档供实测，禁止代填数据）。

**Q7-38：uv 是什么？比 pip 好在哪？**

> **标准回答**：Astral 出品的新一代 Python 包管理器，Rust 实现：解析依赖和安装快 10-100 倍、统一管理 Python 版本/虚拟环境/依赖锁定（pyproject.toml + uv.lock，类似 Cargo）、项目级工具（uv run）。项目从创建到门禁全部走 uv，是 2024-2025 年 Python 生态的主流演进方向。

**Q7-39：你了解的"幂等"是什么？哪些场景要幂等？**

## 8. 系统设计题

> 字节后端/Agent 岗常见开放设计题。每题给出"答题骨架"（背诵结构），结合项目实例加分。设计题核心是**结构化思考**：需求澄清 → 规模估算 → 架构分层 → 数据模型 → 关键流程 → 瓶颈与扩展 → 一致性/可靠性。

**Q8-1：设计一个企业知识库问答系统（RAG 平台）——最可能考，就是你的项目放大版**

> **标准回答**（骨架）：
> 1. **需求澄清**：问清楚规模（文档量级、QPS、并发会话数）、数据形态（PDF/Word/扫描件）、实时性要求（索引延迟）、权限要求（多租户？）。示例假设：100 万文档、1 万 QPS、秒级索引延迟。
> 2. **数据流**：离线索引链路（上传 → 解析 → 分块 → embedding → 写向量库 + 倒排索引；异步任务队列）；在线链路（query 改写 → 混合检索 → rerank → prompt 组装 → LLM 生成 → 流式返回）。
> 3. **组件选型**：向量库（亿级用 Milvus 集群 + HNSW 分片，百万内 FAISS/Qdrant 够）、倒排（Elasticsearch 或 BM25）、缓存（Redis，热点 query）、对象存储（MinIO/S3，原文 + 分块元数据）、任务队列（Kafka/Redis Stream 按量级）、PG（业务元数据 + 会话 + 记忆）。
> 4. **关键设计**：分块策略（业务语义感知，法律/技术文档不同粒度 + 父子块）；混合检索 + RRF；rerank 两级（粗排 bi-encoder → 精排 cross-encoder，top-100 精排 top-10）；检索缓存 + 索引增量更新（文档版本 + 失效）；权限过滤（chunk 带租户 metadata，检索表达式过滤）。
> 5. **可靠性**：索引失败重试 + DLQ；向量库异常降级 BM25；embedding 服务限流 + 批量；检索为空时拒答或注明模型知识。
> 6. **可观测与评测**：trace_id 全链路 + 检索/生成/端到端分层指标 + golden set 回归 + 线上 bad case 回流。
> **加分**：主动提"数据质量决定 RAG 天花板（解析/分块占影响最大）"；提评测口径的坑（文档级 vs chunk 级判定）。

**Q8-2：设计一个多 Agent 编排平台**

> **标准回答**（骨架）：1) 角色模型：主 Agent（规划/汇总）+ 子 Agent（执行，带独立工具域和上下文）；2) 编排模型：Plan-and-Execute（一轮规划 + 并发执行）或 DAG 多阶段；3) 状态与持久化：Agent run 状态机（pending/running/success/failed）+ checkpoint（断点续跑）；4) 并发控制：信号量限流（并发子任务上限）、超时、优雅降级；5) 工具治理：执行域隔离（谁可见什么工具）+ 权限校验 + 审计；6) 可观测：每个子任务 trace、token 成本核算；7) 安全：子任务沙箱（文件/网络/命令隔离）、prompt 注入防护。**加分**：讲"规划可执行性"——主 Agent 只能拆"工具可达"的任务（对应项目的 available_tools 注入）；讲规模必要性——并发收益公式 1 - 最慢/总耗时。

**Q8-3：设计一个限流器（Rate Limiter）**

> **标准回答**（骨架）：1) 算法对比：固定窗口（简单但临界突刺）、滑动窗口（精确但内存多）、令牌桶（允许突发，平滑）、漏桶（恒定速率）；2) 存储：单机内存计数（AtomicCounter）、分布式 Redis（INCR + 过期，或 Lua 脚本原子操作）；3) 我的项目实现：RateLimitMiddleware，每 IP 每分钟 60 次（固定窗口），超限返回 429 JSON（中间件直接返回，不 raise——中间件异常不被 exception_handler 捕获，这是我踩过的坑），健康路径豁免，Redis 不可用降级放行；4) 被追问"多实例怎么限流"：Redis 原子计数 + 时钟一致性注意；5) 被追问"限流和熔断/降级区别"：限流挡入口流量，熔断挡下游故障扩散，降级是兜底策略，三者组合。

**Q8-4：设计一个异步文档索引/任务处理系统**

> **标准回答**（骨架）：1) 触发：上传 API → 入队；2) 队列选型：Redis Stream（中小量）/ Kafka（大量、需分区顺序）；3) 消费者：独立 worker 进程、消费组、ACK、重试（3 次）、DLQ；4) 幂等：doc/chunk 唯一键，重复消费不重复建索引；5) 一致性：以 DB 为事实源，Milvus/BM25 可重建；6) 扩展：多 worker 水平扩展（消费组分片）；7) 监控：队列积压量、消费延迟、失败率告警。**加分**：讲 at-least-once + 幂等的关系；讲"为什么选 Stream 不选 Celery"（项目真实决策）。

**Q8-5：设计一个 Deep Research / 报告生成系统**

> **标准回答**（骨架）：1) 流水线：大纲 → 并行调研 → 证据融合 → 分章撰写 → 三级审查 → 发布；2) 调研预算控制：迭代轮数上限、每轮查询数上限、证据条数阈值（我的 _EVIDENCE_SUFFICIENT_THRESHOLD=12）；3) 防幻觉：强制 [n] 引用 + 规则校验（引用越界/过短）+ LLM 支持度校验 + 主动事实核查（陈述反向检索验证）；4) 并行：章节并行撰写（asyncio.gather + 超时）；5) 后台任务 + 进度推送（SSE/轮询）；6) 落库落盘（对象存储）；7) 评测：引用覆盖率、Grounding 幻觉率、章节完整性。

**Q9-12：实现余弦相似度**

```python
def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = sum(x * x for x in a) ** 0.5
    nb = sum(y * y for y in b) ** 0.5
    return dot / (na * nb) if na and nb else 0.0
```

> 追问延伸：为什么文本 embedding 归一化后内积=余弦；维度大怎么优化（numpy 向量化 / 截断近似）。

**Q9-13：拓扑排序 + 环检测（工具依赖解析核心）**

```python
from collections import deque, defaultdict
def topo_sort(n, edges):  # edges: [(a,b)] a 依赖 b
    g, indeg = defaultdict(list), [0] * n
    for a, b in edges:
        g[b].append(a); indeg[a] += 1
    q = deque([i for i in range(n) if indeg[i] == 0])
    order = []
    while q:
        u = q.popleft(); order.append(u)
        for v in g[u]:
            indeg[v] -= 1
            if indeg[v] == 0: q.append(v)
    return order if len(order) == n else None  # None 说明有环
```

> 项目里的 DependencyResolver 是 DFS 三色标记版本，Kahn 算法版本也要能默写。追问：有环怎么定位环上的节点（记录 DFS 栈）。

**Q9-14：LRU / 计数器 / 限流器（固定窗口）**

```python
# 固定窗口限流（项目 RateLimitMiddleware 核心逻辑）
import time
class FixedWindow:
    def __init__(self, limit, window): self.limit, self.window, self.win_start, self.count = limit, window, time.time(), 0
    def allow(self):
        now = time.time()
        if now - self.win_start >= self.window:
            self.win_start, self.count = now, 0
        if self.count >= self.limit: return False
        self.count += 1; return True
```

> 追问：滑动窗口怎么做（时间戳列表 + 二分）、令牌桶怎么做（令牌数 + 上次补充时间）。

### 12.2 面试当天

- 自我介绍控制在 60-90 秒，结尾主动引导："我重点讲一下工具治理和编排这两块"；
- 被问"部署了几台机器/有没有线上数据"：**诚实回答**（个人项目、本地评测、口径透明）+ 展示评测体系的可复现性；
- 被问不熟悉的问题：先说思路 → 不会就说"这块我了解不深，我理解是……"，不要硬编；
- 数字口径要背熟：33.6%（文档级）/ 23%（chunk 级）、0.68/0.87、-43.4%/-45.2%/100%、65.6%/84.1%——**每个数字都要能说清"怎么测的、什么口径"**；
- 反问环节必问 1-2 个高质量问题。
